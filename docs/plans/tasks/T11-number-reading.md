# T11 한국어 숫자 발음 교정 — 스펙 V1

- 상태: 사용자 확인 2026-11-18 ("확인, 계획으로"). 계획 리뷰 반영으로 3·4·5절 문장을 다듬음(범위 변경 없음)
- 요구사항: REQ-07, 요구사항 5절 수용표, 백로그 P0-12·13
- 로드맵: [T11](../implementation-roadmap.md) — 이 스펙으로 범위를 좁힌다(7절)
- 화면 브리프: [docs/briefs/studio.md](../../briefs/studio.md)의 T11 절(브리프 행에서 쓴다)

## 1. 목표

문단 작업실 대본의 숫자를 사람이 원하는 대로 읽게 한다. 앱이 숫자마다 한글 읽기를 제안하고, 사용자는 항목마다 적용·원문 유지·직접 입력·되돌리기를 고른다. 원문은 그대로 두고, 고른 결과를 반영한 **발음용 대본**만 공급자에게 보낸다.

성공은 이렇게 본다.
- 요구사항 5절 수용표의 11가지 입력이 표대로 제안되거나, 표가 "확인 필요"라고 한 것은 자동으로 정해지지 않는다(자동 테스트).
- 원문을 고친 문단은 그 문단의 검수만 다시 해야 하는 상태가 된다.
- 만들기 전에 검수 안 한 숫자가 있으면 알려 주고, 원문대로 만들지 검수할지 고르게 한다.
- 글자 수, 상한 검사, 예상 사용량, 저장된 소리의 조합 키는 발음용 대본 기준이다.
- 교정은 공급자를 부르지 않는다. 유료 호출은 사용자가 만들기를 눌렀을 때만 일어난다.

## 3. 교정 항목 모델

**교정 항목**은 원문에서 읽기 방식을 정해야 하는 숫자 표기 한 곳이다. 엔진이 원문에서 항목을 찾고(순수 함수), 사용자의 결정만 저장한다.

- 항목 = `{ start, end, original, kind, readings[], needsCheck }`
  - `kind`: 규칙 종류(전화번호, 날짜, 시간, 금액, 단위 수량, 비율, 소수, 음수·온도, 범위, 분수·식, 제품·버전, 일반 수).
  - `readings`: 제안 읽기 목록. 첫째가 기본 제안이다. 둘 이상이면 고른다(예: 공/영, 영하/마이너스).
  - `needsCheck`: 애매해서 자동으로 정하지 않는 항목(범위, 분수·식, 제품·버전, 문맥 없는 음수, `번`처럼 셈과 번호가 갈리는 단위). 기본 제안이 없거나 있어도 "확실한 것 모두 적용"에서 빠진다.
  - 신뢰도 퍼센트는 계산하지 않으므로 보이지 않는다(요구사항 5절 3번).
- 결정 = `{ start, end, original, choice: "apply" | "keep" | "manual", reading? }` — 문단에 `fixes?: { text, decisions }`로 저장한다(`text`는 결정할 때의 원문). 결정이 없으면 그 항목은 **검수 안 함**이다.
- **발음용 대본** = 원문에서 `apply`·`manual` 결정 자리만 그 읽기로 바꾼 글. `keep`과 검수 안 함은 원문 그대로다.
- **무효화**: 문단의 원문이 바뀌면(직접 입력, 붙여 넣기, 태그 넣기, 자동 태그, 나누기·합치기) 그 문단의 결정을 모두 지운다(`fixes.text`가 지금 원문과 다르면 결정 전체가 무효). 다른 문단은 그대로다. 결정마다 `original`이 원문의 그 자리와 다르면 쓰지 않는 검사도 한다(읽을 때의 방어).
- 저장: 기존 임시 작업(`tts-pilot:studio:v2:work`)의 문단에 `fixes`를 더한다. 예전 작업(결정 없음)은 그대로 읽힌다. 서버·DB는 바꾸지 않는다.
- 문단 작업실이 태그로 보는 범위(`SEND_TAGS`: `[영문 태그]`, `<영문 태그>`) 안의 숫자는 항목으로 잡지 않는다. 한글이 든 괄호는 대본 글이라 그 안의 숫자는 잡는다.
- 원문이 결정 때와 같은 글로 돌아오면(되돌리기 등) 그 결정은 다시 유효하다. 엔진 규칙이 바뀌어 지금 항목과 위치·글이 맞지 않는 결정은 쓰지 않는다.

## 5. 화면과 흐름

### 5.1 문단 카드
- 원문 칸은 그대로다.
- 원문 칸 아래 줄(글자 수 줄)에 검수 상태를 보인다. 항목이 없는 문단은 아무것도 보이지 않는다.
  - 검수 안 한 항목이 있으면 "숫자 N개 검수 안 함 · 검수하기". 누르면 숫자 검수 창이 이 문단의 첫 미검수 항목에서 열린다.
  - 모두 검수했으면 "숫자 검수 끝 · 다시 보기".
- 적용(`apply`·`manual`)한 항목이 하나라도 있으면 원문 칸 아래에 읽기 전용 **발음용 대본** 줄을 보인다. 바뀐 부분을 강조하고, 원문과 같으면 보이지 않는다.
- 글자 수와 상한 경고는 발음용 대본 기준이다. 둘이 다르면 "발음용 대본 N자"로 쓴다. 발음용 대본(복사·글자 수)은 태그를 포함한 글이다. 받지 않는 태그를 빼는 일은 지금처럼 요청을 만들 때 한다.

### 5.2 숫자 검수 창
- 작업 띠(위 막대)에 "숫자 검수 N"(검수 안 한 항목 수)을 둔다. 0이면 숨긴다. 누르면 첫 미검수 항목에서 연다.
- 창은 대본 전체의 항목을 문단 순서로 보인다. 한 항목씩 집중하는 화면에 남은 수("남은 3/7")를 둔다.
  - 문단 번호와 앞뒤 문맥(원문 발췌, 항목 강조).
  - 선택지: 제안 읽기들(라디오), 원문 유지, 직접 입력(글 칸), AutoTag 참고 후보(있을 때).
  - 확인 필요 항목은 "확인 필요"와 이유(범위·분수·제품명 등)를 보이고 기본 선택이 없다.
  - 적용·다음, 이전, 되돌리기(그 항목을 검수 안 함으로).
- "확실한 것 모두 적용": 확인 필요가 아닌 미검수 항목에 기본 제안을 적용한다. 10초 되돌리기 알림(기존 `undoable`) 하나.
- "발음용 대본 복사": 모든 문단의 발음용 대본을 문단 사이 빈 줄로 이어 복사한다.
- 창이 열린 동안 원문은 바뀌지 않는다(창은 모달). 만들기 중에는 창의 적용을 잠근다(문단 글이 바뀌는 다른 일과 같은 규칙).

### 5.3 만들기
- 검수 안 한 항목이 있는 문단을 만들 때(한 문단·모두 만들기 모두) 확인 창: "숫자 N개를 검수하지 않았어요. 검수하지 않은 숫자는 원문대로 보내요." → "검수하기"(창 열기) / "원문대로 만들기".
- 확인 창의 예상 사용량은 발음용 대본 기준이다.
- 보내는 글이 바뀐 문단은 조합 키가 달라져 저장된 소리가 낡은 것이 된다(기존 규칙 그대로).

## 6. 오류와 경계

- 직접 입력이 비었거나 공백뿐이면 적용할 수 없다. 숫자를 그대로 넣어도 막지 않는다(사용자 선택).
- 발음용 대본이 상한(공급자별 2,000자, Airy 1,600자)을 넘으면 기존 상한 경고·만들기 막기를 그대로 쓴다.
- 읽은 작업의 결정이 원문과 맞지 않으면(다른 탭 편집 등) 그 결정은 버린다.
- AutoTag 불러오기 실패, 예외: 참고 후보 없이 계속한다. 앱이 `console.error`를 부르지 않는다(청크 실패 때 브라우저가 남기는 네트워크 줄은 앱 오류가 아니다).

## 7. 범위

### 포함
- 자체 숫자 읽기 엔진(4절)과 수용표 전체 자동 테스트.
- 교정 항목 찾기, 결정 저장·무효화, 발음용 대본 만들기, 발음용 대본 기준 글자 수·사용량.
- 문단 카드 검수 상태 줄·발음용 대본 줄, 작업 띠 "숫자 검수 N", 숫자 검수 창, 확실한 것 모두 적용·되돌리기, 발음용 대본 복사, 만들기 전 미검수 확인.
- AutoTag 참고 후보(의존성 추가, ADR).
- GLOSSARY(교정 항목·숫자 검수), `docs/domain/project.md` 작업실 절, 로드맵·REQ-08 메모.

### 만들지 않는 것 (ponytail)
- 드라마 작업실 교정 → 백로그(같은 엔진을 줄 읽기·장면 요청에 붙인다).
- 프리셋 교정 모드 → P1-07과 함께.
- 원문을 고쳐도 결정을 옮겨 살리는 재매칭(같은 숫자가 그대로 있으면 유지) → 백로그. V1은 그 문단 결정을 지운다.
- 개인 발음 사전, 숫자 외 표기(영문 약어, 고유명사) 교정 → P1-07.
- 서버 저장·생성 기록에 원문 보관(지금 `trial_generation.text`는 보낸 글) → T12 대본 보관함에서 원문 저장과 함께 본다.
- LLM 교정, 신뢰도 점수, 문장 단위 미리 듣기(만들기 = 유료 호출이라 기존 만들기만).
- 원문 칸 안 밑줄 강조(뒤판) — 카드에는 발음용 대본 줄만.

## 8. 구조 (계획에서 확정)

- 서버(`packages/api`)·DB(`packages/db`)는 바꾸지 않는다.

## 9. 수용 기준

1. 수용표 11행이 4절 표대로 제안되고, 확인 필요 항목은 "확실한 것 모두 적용"으로 정해지지 않는다.
2. 적용·원문 유지·직접 입력·되돌리기가 항목마다 되고, 발음용 대본이 즉시 바뀐다.
3. 한 문단의 원문을 고치면 그 문단 결정만 지워지고 상태 줄이 "검수 안 함"이 된다.
4. 카드 글자 수·상한·예상 사용량·만들기 요청 글이 모두 발음용 대본이다.
5. 검수 안 한 항목이 있는 문단 만들기는 확인 창을 거친다. "원문대로 만들기"는 그 항목을 원문으로 보낸다.
6. 발음용 대본 복사가 모든 문단의 발음용 대본(태그 포함)을 복사한다.
7. 새로 고침 뒤에도 결정이 남고, 예전 작업도 그대로 열린다.
8. 교정·검수 동작은 공급자 호출 0회다.

## 10. 자동 테스트 (vitest)

- `number-reading.test.ts`: 수용표 11행, 만·억 띄어쓰기, 고유어 1~99와 100 이상 조합, 6월·10월, 시간 경계(24:00, 3:60은 시간 아님), 겹침 방지(전화번호 안의 숫자를 다시 잡지 않음), 태그 안 숫자 제외, 이미 한글 대본·두 번 적용해도 같은 결과, 줄바꿈 보존.
- `paragraph-script.test.ts`: 발음용 대본 만들기(여러 결정, 순서), 원문 변경 시 무효화, `original` 불일치 결정 무시, `paragraphRequest` 글이 발음용 대본, 사용량·조합 키가 요청 글을 따름, 겹치거나 낡은 결정은 무시.
- `studio-draft.test.ts`: `fixes` 있는/없는 작업 읽기, 잘못된 결정 버림.
- 확실한 것 모두 적용이 확인 필요를 건너뜀, 되돌리기.

## 11. 테스트 시나리오 (브라우저 QA, 가짜 응답, 유료 호출 0회)

- 정상: 수용표 예시 대본 붙여 넣기 → 카드 상태 줄 → 창에서 항목별 적용·유지·직접 입력·되돌리기 → 발음용 대본 줄 강조 → 복사.
- 빈 상태: 숫자 없는 대본(상태 줄·버튼 없음), 빈 문단.
- 무효화: 검수 뒤 원문 한 글자 고침, 태그 넣기, 나누기·합치기.
- 만들기: 미검수 확인 창의 두 선택(전체 창과 한 문단 창), 요청 본문 글이 발음용 대본(가짜 응답으로 확인), 만들기 중 검수 창 적용 잠김, 성우 캐스팅 확인 창 회귀.
- 경계: 상한 근처에서 읽기가 길어져 넘는 경우. AutoTag 불러오기 실패는 단위 테스트(vi.mock)로 확인하고 브라우저에서는 만들지 않는다.
- 너비 1440·768·390·320, 라이트·다크, 키보드만(창 열기·라디오·직접 입력·다음·Esc), 스크린리더 이름.

## 12. 사용자 테스트 (구현 뒤 드린다)

1. 수용표 예시가 든 대본을 문단 작업실에 붙여 넣는다.
2. 숫자 검수 창에서 항목을 적용·유지·직접 입력·되돌리기 해 본다. AutoTag 참고 후보와 비교한다.
3. 카드의 발음용 대본 줄과 글자 수를 확인하고, 원문을 고쳐 재검수 상태가 되는지 본다.
4. 원하면 한 문단을 만들어 듣는다(유료 호출, 그때 승인).

## 13. 위험과 확인할 것

- 공급자 자체 정규화가 발음용 대본을 다시 바꿀 수 있다(요구사항 5절 6번). 청취로만 확인할 수 있어 자동 테스트로 약속하지 않는다.
- AutoTag 패키지 크기(설치본 6.5MB)와 번들 영향, 브라우저 실행 가능 여부 → 계획에서 확인하고, 안 되면 결정 1을 다시 묻는다.
- 고유어 단위 표는 완전하지 않다. 모르는 단위는 한자어로 읽고, 사용자가 고친다.
