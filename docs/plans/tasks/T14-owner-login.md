## 1. 목표

로컬 관리자 모드(로그인 없이 개발 서버 루프백 주소에서만 소유자를 주는 방식)를 없애고, 본인 한 명이 이메일·비밀번호로 로그인해야 작업실을 쓰게 한다. 소유자는 서버 환경 변수 `OWNER_EMAILS`의 이메일 한 개와 같은 계정이다. 공개 가입은 서버에서 막고, 계정은 로컬 DB에서만 도는 스크립트로 만든다. 지금 로컬 DB에 `local-admin`으로 쌓인 데이터는 계정을 만들 때 그 계정으로 옮긴다. 이것으로 production에서도 보호 프로시저가 동작할 수 있게 되어 T15 배포의 전제가 선다.

## 3. 인증 사실 (설치판 better-auth 1.7.5, 2026-11-18 조사)

- `emailAndPassword.disableSignUp: true`이면 `/api/auth/sign-up/email` HTTP 요청과 서버 `auth.api.signUpEmail`이 같은 핸들러에서 400 `EMAIL_PASSWORD_SIGN_UP_DISABLED`로 막힌다(`dist/api/routes/sign-up.mjs:144-147`).
- 가입을 막은 채 계정을 만드는 길은 `auth.$context`의 `password.hash`, `internalAdapter.createUser`, `internalAdapter.linkAccount({ providerId: "credential", accountId: user.id, password })`다(가입 핸들러와 같은 순서, `sign-up.mjs:221-247`). 이 길은 이메일 형식·길이·비밀번호 길이 검사를 하지 않으므로 스크립트가 직접 한다. 해시는 scrypt.
- 세션: 만료 7일, 갱신 1일, 쿠키 캐시 꺼짐. 쿠키 `better-auth.session_token`(httpOnly, `sameSite=lax`, path `/`). `BETTER_AUTH_URL`이 `http://`이면 secure·`__Secure-` 없이 발급되어 `http://127.0.0.1:3001`에서 그대로 동작한다.
- 속도 제한: production에서만 기본으로 켜진다. `/sign-in*`은 10초에 3회, 저장소는 메모리(인스턴스마다 따로). 개발에서는 꺼져 있다.
- 출처 검사: 쿠키가 있는 POST는 `Origin`이 `trustedOrigins`(지금 `BETTER_AUTH_URL` 하나)와 정확히 맞아야 하고, 아니면 403. **`localhost`와 `127.0.0.1`은 출처가 달라서, 지금 `apps/web/.env`의 `BETTER_AUTH_URL=http://localhost:3001`이면 `http://127.0.0.1:3001`로 연 화면의 로그인은 403이다.** 개발 주소는 `BETTER_AUTH_URL`과 같은 주소(지금 `http://localhost:3001`) 하나로 쓴다(8절).
- 세션 읽기: 서버는 `auth.api.getSession({ headers })`(없으면 null). `better-auth/cookies`의 `getSessionCookie`는 쿠키가 있는지만 보고 검증하지 않는다.

## 4. 소유자 결정 (서버)

- `apps/web/src/context.ts`가 요청마다 `auth.api.getSession({ headers: req.headers })`로 세션을 읽는다. 세션 사용자의 이메일이 소유자 이메일과 같으면 `ownerId = 세션 user.id`, 아니면 `null`이다. 공급자 클라이언트는 지금처럼 `ownerId`가 있을 때만 만든다. `protectedProcedure`와 모든 라우터는 바꾸지 않는다(`ownerId`만 본다).
- 소유자 이메일: `OWNER_EMAILS`를 쉼표로 나누고 앞뒤 공백을 지우고 소문자로 바꾸고 빈 값을 버린 뒤 중복을 없앤다. 남은 값이 정확히 하나면 그것이 소유자 이메일이다. 0개면 소유자 없음. 2개 이상이면 소유자 없음이고, 서버가 처음 판정할 때 "OWNER_EMAILS에 이메일이 둘 이상이라 모두 거부합니다" 한 줄을 남긴다(이메일 값은 로그에 쓰지 않는다). 세션 사용자 이메일도 같은 방식으로 정리해 비교한다.
- `NODE_ENV`·Host 검사(`localOwnerId`, `LOCAL_OWNER_ID`)를 없앤다. production에서도 소유자가 정해진다. DNS 리바인딩으로 남의 도메인이 127.0.0.1을 가리켜도 세션 쿠키는 그 도메인에 붙지 않아 소유자가 없다.
- `OWNER_EMAILS`는 `apps/web/.env.schema`에 서버 전용(`@sensitive`, `@optional`, 문자열)으로 선언한다. 없거나 비면 모두 거부한다. 클라이언트로 보내지 않는다.
- oRPC CSRF(`SimpleCsrfProtectionHandlerPlugin`)는 그대로 둔다. 이제 로그인 쿠키가 있으므로 이 방어가 실제 쿠키 요청을 막는다(route 주석의 '쿠키가 없다' 전제를 고친다).

## 5. 화면과 흐름

### 5.1 로그인 `/login`

- 메뉴(앱 틀) 없이 화면 가운데 작은 판 하나: 제품 이름, 이메일, 비밀번호, '로그인'. 가입·비밀번호 찾기 링크는 없다.
- 성공하면 `next`로 간다. `next`는 `/`로 시작하고 `//`·`/\`로 시작하지 않으며 `/login`이 아닌 앱 안 경로만 받는다. 아니면 `/studio`.
- 이미 로그인한 소유자가 `/login`을 열면 `next`(없으면 `/studio`)로 보낸다. 로그인했지만 소유자가 아니면 5.3 화면.
- 실패 문구: 이메일·비밀번호가 틀리거나 없는 계정이면 "이메일이나 비밀번호가 맞지 않아요."(어느 쪽인지 말하지 않는다). 너무 자주 시도하면(429) "잠시 뒤 다시 시도해 주세요." 출처 불일치(403)면 "이 주소에서는 로그인할 수 없어요. {BETTER_AUTH_URL의 출처}로 열어 주세요."(개발 주소 혼동). 그 밖은 "로그인하지 못했어요. 잠시 뒤 다시 시도해 주세요."
- 보내는 동안 버튼을 잠그고 두 번 보내지 않는다.

### 5.2 보호

- 로그인하지 않았거나 세션이 끝난 채로 앱 화면(`/`과 `(app)` 아래 모든 페이지, 없는 주소 화면)을 열면 `/login?next=<열려던 경로와 검색어>`로 보낸다. `/login`, `/api/*`, 정적 파일은 보내지 않는다.
- 페이지는 서버에서 세션을 확인하고 보낸다(클라이언트 리다이렉트만으로 막지 않는다). 데이터는 지금처럼 `protectedProcedure`가 막는다.

### 5.3 접근 권한 없음

- 세션은 있지만 소유자가 아니면(허용 목록이 바뀌었거나 둘 이상이라 거부, 목록이 빔) 앱 화면 대신 메뉴 없는 가운데 판: 제목 "접근 권한 없음", "{이메일} 계정은 이 작업실을 쓸 수 없어요.", '로그아웃' 버튼. 로그아웃하면 `/login`.

### 5.4 메뉴 아래 줄

- '로컬 관리자' 글자 자리에 로그인한 이메일(길면 말줄임, 마우스를 올리면 전체). 테마 버튼 옆에 '로그아웃' 버튼(`LogOut` 아이콘, 접근 이름 "로그아웃"). 순서는 이메일 → 로그아웃 → 테마(보이는 순서 = Tab 순서는 브리프에서 확정). 767px 이하 더보기 안 줄도 같다.
- 로그아웃은 세션을 지우고 `/login`으로 간다. 실패하면 줄 아래 한 줄 "로그아웃하지 못했어요. 다시 시도해 주세요."

### 5.5 쓰는 중 세션이 끝남

- 보호 프로시저가 `UNAUTHORIZED`를 주면 지금 화면마다 보이는 '개발 서버를 127.0.0.1로 열어 주세요' 안내(`LoopbackNotice`)를 "로그인이 풀렸어요" + "다시 로그인하면 이 화면으로 돌아와요." + '다시 로그인' 버튼(`/login?next=<지금 경로와 검색어>`, 전체 이동)으로 바꾼다(critique 반영 2026-11-18). 한 컴포넌트만 바꾼다.
- 알려진 한계(QA P2, 사용자 "백로그로" 2026-11-18): 목록을 다시 불러오다 `UNAUTHORIZED`가 나면 화면 본문이 안내로 바뀌어 열려 있던 창과 그 입력이 사라진다. 서버 데이터는 그대로이고, 작업실·드라마의 대본은 브라우저 임시 작업에 남는다. 백로그 T14-02.

## 6. 계정 만들기 스크립트

- 명령: `pnpm owner:create`(이름은 계획에서 확정). 사용자가 터미널에서 직접 실행한다(Claude Code에서는 `! pnpm owner:create`).
- 거부(아무것도 쓰지 않고 이유 한 줄, exit 1):
  - `NODE_ENV`가 production.
  - `DATABASE_URL`의 호스트가 `localhost`·`127.0.0.1`·`::1`이 아니다(원격 DB). 주소 값은 출력하지 않는다.
  - 입력한 이메일이 4절 규칙으로 정한 소유자 이메일과 다르다(목록이 비었거나 둘 이상인 경우 포함). 허용 목록 밖 계정은 만들지 않는다.
  - 같은 이메일 계정이 이미 있다: "이미 있는 계정이에요. 바꾸지 않았어요."
  - 비밀번호가 12자 미만이거나 128자 초과, 두 번 입력이 다르다.
- 입력: 이메일은 일반 입력, 비밀번호는 터미널에서 화면에 보이지 않게 두 번. 터미널이 아니면(파이프) 표준 입력 1줄 이메일, 2·3줄 비밀번호로 읽는다(브라우저 QA가 테스트 DB에 QA 계정을 만들 때 쓴다. 인자·환경 변수는 받지 않는다). 이름은 이메일 `@` 앞부분.
- 만들기: 3절 길(해시 → `createUser` → `linkAccount`), 이메일은 4절 규칙으로 정리한 값.
- 옮기기: 계정을 만든 같은 실행에서 한 트랜잭션으로 `owner_id = 'local-admin'`인 행을 새 계정 id로 바꾼다. 대상은 `channel`, `classification`, `saved_voice`, `voice_preset`, `script`, `trial_generation`, `my_voice`. `provider_list_cache`의 `local-admin` 행은 캐시라 옮기지 않고 지운다. 연결 표(`saved_voice_channel` 등)는 id로 이어져 그대로다. 새 계정에는 행이 없으므로 유일 제약 충돌이 없다.
- 계정과 이전은 함께 성공하거나 함께 실패한다. 이전이 실패하면 만든 계정을 지우고 실패를 알린다.
- 출력: "계정을 만들었어요." + 표마다 옮긴 행 수(숫자만). 비밀번호·해시·DB 주소는 출력하지 않는다.

## 7. 소유권과 보안 (REQ-01, better-auth-security)

- 소유자 id는 세션 + 소유자 이메일에서만 온다(4절). 클라이언트 입력으로 소유자를 받지 않는다.
- 가입은 서버에서 막힌다(HTTP·서버 호출 모두). 가입 화면·링크가 없다.
- 계정은 허용 목록의 한 이메일로만, 로컬 DB에서만 만들어진다(6절).
- 로그인 실패 문구는 계정이 있는지 드러내지 않는다.
- `BETTER_AUTH_SECRET`(32자 이상)·`BETTER_AUTH_URL`은 지금 그대로. `trustedOrigins`는 `BETTER_AUTH_URL` 하나 그대로. 출처·CSRF 검사를 끄는 옵션을 쓰지 않는다.
- 공급자 키는 소유자 요청에만 쓰인다(4절 그대로). 소유자가 한 명이라 '단일 소유 예외'(시험 생성·작업실·드라마의 공급자 voice id 소유권, 성우 캐스팅 '내 계정', 자동 태그 횟수)는 그대로 유효하다. 여러 소유자를 받을 때 함께 다룬다(9절).
- 속도 제한은 production 기본값(메모리, 10초 3회)에 맡긴다. 배포(T15)에서 함수 인스턴스마다 따로인 한계를 다시 본다.

## 8. 오류와 경계

| 경우 | 동작 |
|---|---|
| `OWNER_EMAILS` 없음·빈 값 | 로그인은 되지만 모든 사용자가 5.3. 스크립트는 거부 |
| `OWNER_EMAILS`에 서로 다른 이메일 둘 이상 | 위와 같고 서버 로그 한 줄 |
| `OWNER_EMAILS="  Me@Example.com , me@example.com "` | 하나로 정리(`me@example.com`), 정상 |
| `BETTER_AUTH_URL`과 다른 루프백 주소(`127.0.0.1` ↔ `localhost`)로 열고 로그인 | 403 → 5.1의 출처 문구(`BETTER_AUTH_URL` 주소 안내) |
| `next=https://evil.example`, `next=//evil`, `next=/\evil` | 무시하고 `/studio` |
| 세션 만료 뒤 화면 이동 | `/login?next=…` |
| 세션 만료 뒤 같은 화면에서 저장·생성 | 5.5 안내, 입력은 남는다 |
| 로그인한 채 허용 목록에서 빠짐 | 다음 요청부터 5.3·`UNAUTHORIZED` |
| DB가 멈춤 | 화면은 세션을 읽지 못해 전역 오류 화면("문제가 생겼어요" + '다시 시도'), rpc는 500(예상 밖 오류라 화면의 일반 오류 안내. '로그인이 끝났어요'가 아니다) |
| 이미 계정이 있는데 스크립트 다시 실행 | "이미 있는 계정이에요." 데이터 이전도 하지 않는다 |

- 소유자 결정: `apps/web/src/context.ts`, 소유자 이메일 정리·판정 함수(지금 `packages/api/src/owner.ts` 자리), `apps/web/.env.schema`의 `OWNER_EMAILS`.
- 인증 설정: `packages/auth/src/index.ts`(`disableSignUp`), 클라이언트 `apps/web/src/lib/auth-client.ts`(새).
- 화면: `/login` 페이지, 앱 틀을 메뉴 있는 묶음과 없는 화면으로 나누기(지금 루트 layout에 메뉴가 있다), 보호(Next 16 `proxy.ts` 또는 layout의 서버 확인 — 번들 문서 기준으로 계획에서 고른다), `app-nav.tsx` 아래 줄, `notice.tsx`의 안내.
- 스크립트: 위치와 TS 실행 방법(11절 수용 기준 13). 저장소의 `.ts` 패키지는 확장자 없는 상대 import라 Node 기본 타입 지우기로는 돌지 않는다. 이미 설치된 `jiti`(간접 의존 2.7.0)를 직접 개발 의존으로 올리는 안을 먼저 본다.

## 11. 수용 기준

1. 로그인하지 않고 `/studio`·`/voices?x=1` 등을 열면 `/login?next=…`로 간다. `/login`·`/api/*`는 보내지 않는다.
2. 소유자 이메일·비밀번호로 로그인하면 `next` 화면(없으면 `/studio`)이 열리고 모든 화면이 지금처럼 동작한다(이전한 데이터가 보인다).
3. 틀린 비밀번호·없는 이메일은 같은 문구 "이메일이나 비밀번호가 맞지 않아요."이고 세션이 생기지 않는다.
4. `POST /api/auth/sign-up/email`은 400이고 사용자 행이 생기지 않는다.
5. 허용 목록 밖 계정(또는 목록이 비거나 둘 이상)으로 로그인하면 5.3 화면이고 보호 프로시저는 모두 `UNAUTHORIZED`다.
6. 로그아웃하면 `/login`으로 가고, 뒤로 가기·주소 입력으로 보호 화면을 열어도 `/login`이다.
7. `next`가 앱 밖 주소면 `/studio`로 간다.
8. 메뉴 아래 줄에 이메일과 '로그아웃'이 보이고 '로컬 관리자' 글자가 없다(1440·768·390).
9. 세션을 지운 뒤 같은 화면에서 목록·저장을 부르면 5.5 안내와 로그인 링크가 보인다.
10. production 빌드(`next start`)에서도 소유자로 로그인하면 보호 프로시저가 동작한다(루프백·NODE_ENV 조건이 없다).
11. 스크립트: production·원격 DB·허용 목록 밖 이메일·이미 있는 이메일·짧은 비밀번호를 거부하고 아무것도 쓰지 않는다.
12. 스크립트: 새 계정을 만들고 `local-admin` 행을 모두 옮기며(캐시 행은 지움) 옮긴 수를 출력한다. 비밀번호·해시·DB 주소는 출력·로그에 없다. 이전 실패 시 계정도 남지 않는다.
13. 스크립트는 `pnpm` 명령 하나로 돈다.
14. 타입·린트·빌드·API·화면 테스트가 통과하고, 기존 2계정 격리 테스트는 바꾸지 않고 통과한다.

## 12. 자동 테스트 (vitest)

- 소유자 이메일 정리·판정: 빈 값, 공백·대소문자, 중복 하나로, 서로 다른 둘 이상 거부, 세션 이메일 대소문자.
- context 소유자 결정: 세션 없음 → null, 소유자 세션 → user.id, 다른 이메일 세션 → null, 목록 둘 이상 → null. 판정 함수(`ownerIdOf`) 표 테스트로 덮는다(context는 세션 읽기와 이 함수를 잇기만 한다).
- `next` 정리: 앱 안 경로 통과, `//`·`/\`·절대 주소·`/login` → `/studio`.
- 가입 막기: 테스트 DB에서 `auth.api.signUpEmail`이 거부되고 행이 없다.
- 스크립트 핵심 함수: DB 주소 판정(로컬 셋 통과, 원격 거부), 비밀번호 길이, 이전(테스트 DB에서 `local-admin` 행 7개 표 이동·캐시 행 삭제·다른 소유자 행 그대로·실패 시 롤백과 계정 삭제).
- 기존: `owner.test.ts`의 루프백 테스트는 새 판정 테스트로 바꾼다. 다른 라우터·격리 테스트는 Context를 직접 넣으므로 그대로다.

## 13. 테스트 시나리오 (브라우저 QA)

- QA는 개발 DB와 3001 개발 서버를 건드리지 않는다. 테스트 DB(`tts-pilot-app_test`)·`BETTER_AUTH_URL=http://127.0.0.1:3002`·`OWNER_EMAILS=qa-owner@example.test`를 프로세스 환경으로 준 production 빌드(`next build` → `next start -p 3002`)에 스크립트(파이프 입력)로 QA 계정을 만들고 확인한 뒤 서버를 끈다(Next 16은 같은 폴더에 개발 서버를 둘 띄우지 못한다). 이 실행이 수용 기준 10도 덮는다. 공급자 유료·상태 변경 호출 0회.
- 정상: 비로그인 `/voices` → `/login?next=/voices` → 로그인 → `/voices`. 메뉴 아래 줄 이메일·로그아웃. 로그아웃 → `/login`.
- 오류: 틀린 비밀번호 문구, `BETTER_AUTH_URL`과 다른 루프백 주소 로그인 403 문구, `next=//evil` → `/studio`, 가입 POST 400.
- 권한: `OWNER_EMAILS`를 다른 이메일로 바꿔 다시 띄운 서버에서 QA 계정 로그인 → 접근 권한 없음 → 로그아웃.
- 만료: 쿠키를 지운 뒤 같은 화면에서 목록 새로 고침 → 5.5 안내 → 링크 → 로그인 → 원래 화면.
- DB 멈춤은 자동 테스트 밖이다(전역 오류 화면은 코드 리뷰로 본다). 너비 1440·768·390, 라이트·다크, 키보드만으로 로그인(Tab 순서, Enter 제출, 오류 문구 읽힘 `role="alert"`), 오류 예산 0.

## 14. 사용자 테스트 (구현 뒤)

1. `apps/web/.env`에 `OWNER_EMAILS=<본인 이메일>`을 넣는다.
2. 터미널에서 `pnpm owner:create`로 계정을 만든다(비밀번호는 화면에 보이지 않음). 옮긴 행 수를 확인한다.
3. `BETTER_AUTH_URL` 주소(지금 `http://localhost:3001`)로 `/voices`를 연다 → 로그인 화면 → 로그인 → 성우 보관함과 예전 데이터(채널·분류·프리셋·대본·내 보이스)가 보인다.
4. 틀린 비밀번호로 로그인 → 실패 문구.
5. 가입 거부: 안내하는 `curl` 한 줄로 가입 POST → 400.
6. 허용 목록 밖: `OWNER_EMAILS`를 다른 이메일로 바꾸고 서버를 다시 켠다 → 접근 권한 없음 → 로그아웃 → 원래 값으로 되돌린다.
7. 로그아웃 → 보호 화면 주소를 직접 입력해도 로그인 화면.

## 15. 위험과 확인할 것

- **하네스 규칙 변경:** `AGENTS.md`(그리고 `CLAUDE.md`가 포함)와 `tts-provider` 스킬에 '로컬 관리자 모드' 규칙(Server Component의 `getSession` 금지, 보호 페이지 규칙 금지, 루프백 소유자)이 있다. T14가 이 규칙을 바꾸므로 하네스(H) 파일 변경이 생기고 케이스 상향 행이 붙는다.
- **앱 틀 나누기:** 지금 루트 layout이 모든 경로(없는 주소 포함)에 메뉴를 그린다. 메뉴 없는 `/login`·접근 권한 없음 화면을 위해 layout 구조가 바뀐다. 모든 페이지 회귀 QA가 필요하다.
- **개발 주소 하나로:** `localhost:3001`과 `127.0.0.1:3001`이 출처가 다르다. 그동안 둘 다 되던 개발 주소가 `BETTER_AUTH_URL`과 같은 하나(지금 `localhost:3001`)만 로그인된다(5.1 문구로 안내).
- **새 개발 의존:** 스크립트 TS 실행기(10절). 이미 잠금 파일에 있는 `jiti`를 직접 의존으로 올리는 것이 추천안이다. 확인 때 함께 승인받는다.
- **테스트 DB 스키마:** QA가 테스트 DB에 개발 서버를 붙이므로 마이그레이션이 테스트 DB에 적용돼 있어야 한다(지금 API 테스트가 쓰는 DB).
