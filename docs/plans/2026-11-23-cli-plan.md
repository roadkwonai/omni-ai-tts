# Omni AI TTS CLI 기획·설계안

## 목표와 전제

웹에서 담은 성우를 터미널에서 찾고, 같은 프리셋·대본을 사용해 한국어 음성을 만들어 파일로 받는다. 최종 범위는 소유자용 웹 작업실에서 현재 할 수 있는 업무 전체다. 브라우저의 재생·녹음·편집 조작은 파일, 입력 매니페스트, 확인 프롬프트로 대응한다. 공개 랜딩·데모, 화면의 테마·배치, 운영자용 배포·DB 명령은 CLI 제품 범위 밖이다. 공급자별 지원 모델과 기존 백로그 기능의 범위는 해당 기능의 로드맵을 따른다.

설계 기본값은 본인용 원격 작업실과 로컬 개발 서버에 연결하는 개인용 CLI, macOS 우선 검증, 저장소의 pnpm 워크스페이스에서 실행하는 TypeScript 프로그램이다. 실행 파일 이름은 `omni-tts`로 제안한다. 저장소 내 실행을 먼저 제공하고 전역 배포나 별도 레지스트리 발행은 사용 방식이 확인되면 결정한다.

## 대표 사용 흐름

아래는 구현 뒤 제공할 명령 예시다. `typecast:voice-123`은 예시이며 실제로는 목록의 `ref`를 그대로 복사한다. 두 번째 생성 예시는 WAV를 내보내는 프리셋을 가정한다.

```bash
omni-tts auth login --url "$STUDIO_URL"
omni-tts voices list --channel "쇼핑 쇼츠"
omni-tts voices list --favorite --json
omni-tts studio generate --voice typecast:voice-123 --input 대본.txt --out 내레이션.mp3
omni-tts studio generate --preset-id PRESET_ID --input - --out 내레이션.wav --yes < 대본.txt
omni-tts studio download RESULT_ID --out 내레이션.wav
```

`voices list`는 웹처럼 성우 보관함을 읽는다. 이름, 공급자, 성우 참조(`provider:voiceId`), 채널·분류, 즐겨찾기·자주 사용, 이용 가능 여부, 사용 횟수와 최근 사용 시각을 제공한다. 동명이인은 목록에 함께 표시하고 생성은 성우 참조 또는 성우가 지정된 프리셋으로 고른다. 채널명 검색은 정확히 한 채널과 일치할 때 적용하며 여러 결과가 있으면 채널 ID를 안내한다. 카탈로그 검색은 `casting search`로 구분한다. 보관함 조회는 공급자 새로고침 없이 바로 읽고, 상태 갱신은 `voices check`로 실행한다.

웹의 문단 임시 작업은 기기 내 임시 상태이므로 CLI에서는 입력 매니페스트와 로컬 진행 기록으로 다룬다. 저장 대본·보관함·프리셋·서버에 저장된 결과는 같은 작업실에 연결하면 공유된다. 공급자가 샘플을 제공하지 않거나 구간 단서를 제공하지 않는 경우 해당 항목을 명령 결과에 표시한다. 무료 샘플 선택이 자동으로 시험 생성으로 이어지지 않는다.

## 명령 계약

- 사람이 보는 기본 표는 한국어로 표시한다. `--json`은 stdout에 UTF-8 JSON 한 건만 쓰고 진행·경고·확인 프롬프트는 stderr로 보낸다. 목록 스키마에 식별자와 페이지 정보를 포함한다. 실패는 종료 코드와 `{ code, reason, retryAt?, requestId? }`로 구분하고 공급자 원시 오류는 출력에서 제외한다.
- 종료 코드 제안은 `0` 성공, `2` 입력·확인 필요, `3` 세션·소유권, `4` 찾을 수 없음·이용 불가, `5` 공급자·서비스 실패/제한, `6` 처리 여부 미확인, `7` 로컬 파일 실패다. `--help`로 인자, 예시, 과금·삭제 여부를 확인할 수 있다.
- 단일 문단은 UTF-8 파일 또는 `--input -`로 stdin을 받는다. 문단·드라마 묶음은 버전을 명시한 JSON 파일을 사용한다. 단일 생성에서 `--voice`와 `--preset-id`는 상호 배타적이고 프리셋은 성우·모델·설정을 한 번에 가져온다. 성우 직접 지정 시 초기값은 웹의 공급자별 기본 설정을 따른다. 문단·드라마의 입력 오류는 행 번호와 함께 생성 전에 알려 준다.
- 파일형 출력은 `--out`으로 지정한다. 유료 호출 전에 경로·기존 파일·설정에서 알 수 있는 형식을 검사하고, 응답 뒤 실제 MIME과 확장자를 다시 확인한다. 덮어쓰기는 `--overwrite`로 선택한다. `--yes`는 과금·삭제 확인에만 적용한다. 3MiB 조각의 순서·길이·전체 크기를 검증하며 같은 디렉터리의 임시 파일에 쓴다. 기본 동작은 최종 경로에 이미 파일이나 심볼릭 링크가 있으면 게시에 실패한다. 전송 실패나 `Ctrl+C`에 부분 파일을 결과 경로에 남기지 않고 저장 완료한 서버 결과 ID를 안내한다. 다운로드 재시도는 저장된 결과만 읽는다.
- 독립 실행인 `studio download RESULT_ID`의 전체 바이트 수는 신규 보호 조회에서 받는다. 기존 `studioFind/FindMany`는 요청 조합으로 검색하고 `studioAudio`는 조각만 반환한다. 신규 조회는 결과 ID·세션 소유자·종류 `studio`·완료 상태·보관 기한을 기존 조각 조회와 같은 조건으로 검사하고 바이트 수와 MIME만 돌려준다. 다른 소유자, 다른 종류, 만료, 미완료, 없는 결과는 모두 `NOT_FOUND`다. 보관 연장은 기존 첫 조각 다운로드에 맡긴다. 드라마는 테이크 목록과 생성 응답의 바이트 수를 사용한다.

## 구조와 인증

- `apps/cli`에 명령 파싱, 세션 보관, 파일 입출력, 출력과 오류 표시를 둔다. Node의 표준 인자 파서와 기존 oRPC 클라이언트로 시작한다. `AppRouterClient`는 타입으로 참조하고, 런타임에는 클라이언트와 확인된 순수 모듈만 가져온다. 루트 실행 연결은 먼저 `pnpm --filter @tts-pilot-app/cli exec omni-tts` 또는 해당 패키지의 `cli` 스크립트가 실제로 해석되는 경로를 패키지 테스트로 확정한다. [oRPC RPCLink](https://v1.orpc.dev/docs/client/rpc-link)
- `auth login`은 입력이 가려지는 터미널 프롬프트로 기존 이메일·비밀번호를 받아 `/api/auth/sign-in/email`을 호출한다. 응답 쿠키는 동일 origin에만 보내고, 이후 `/api/rpc`의 `savedVoiceList` 보호 조회로 소유자 접근을 확인한 뒤 저장한다. 웹의 `trustedOrigins`, 로그인의 시도 제한, `OWNER_EMAILS` 단일 일치와 oRPC `SimpleCsrfProtectionLinkPlugin`을 사용한다. `auth status`도 보호 조회로 확인하고 `auth logout`은 기존 로그아웃을 호출한다. [Better Auth 이메일 로그인](https://better-auth.com/docs/authentication/email-password) · [Better Auth 보안](https://better-auth.com/docs/reference/security)
- 작업실 주소는 사용자가 명시하고 CLI는 비밀번호 입력 전에 정규화한 origin을 표시한다. HTTPS를 기본으로 하고 로컬 개발용 루프백에만 HTTP를 허용한다. 쿠키와 로그인 정보가 포함된 요청은 리다이렉트를 거절한다. origin별로 세션을 분리하고 갱신·만료 `Set-Cookie`를 반영한다. 요청 시작 시 읽은 세션 버전과 현재 버전이 일치할 때만 갱신 응답을 잠금 아래 저장한다. 로그아웃은 같은 잠금 아래 세션을 폐기하고 버전을 바꾼다. 이미 출발한 요청의 늦은 응답이 로그아웃이나 새 로그인 뒤 이전 세션을 복원할 수 없다. T17은 로컬 HTTP 통합 테스트에서 쿠키 갱신·만료·서버 로그아웃, 늦은 응답, 거절된 로그인과 공개 데모의 로그인 거절을 확인한다. CLI의 서비스 명령은 보호 조회 전에 저장된 세션을 요구한다.
- 첫 구현의 세션 보관은 macOS 사용자 전용 디렉터리(권한 `0700`) 안 파일(`0600`)을 쓰는 안이다. 심볼릭 링크와 느슨한 권한은 거절하고, 원자적으로 저장한다. 자격 증명을 별도로 복제하거나 인자·로그·JSON에 남기는 경로는 제외한다. 원격 로그아웃 실패는 서버에서 세션이 폐기되지 않았을 수 있음을 알리며 로컬 세션은 지운다. 로그인 가능 여부를 실제 배포에 대조하는 작업은 T17의 별도 승인된 확인에 둔다.
- 재사용 정본은 `packages/api/src/routers/`의 각 보호 프로시저와 검증 계약, `packages/auth/src/index.ts`, `apps/web/src/context.ts`, `apps/web/src/utils/orpc.ts`다. `apps/web/src/lib/number-reading.ts`처럼 웹과 CLI에서 똑같이 실행해야 하는 순수 규칙만 소비자가 생기는 단계에서 공용 위치로 옮긴다. `sound-join.ts`의 브라우저 오디오 디코딩 경로는 웹에서 유지하고 CLI는 T20에서 현행 형식의 로컬 결합 수단과 WAV·MP3 혼합 입력을 검증한다. 외부 도구가 필요하면 설치 전제와 근거를 T20 상세 계획에 기록한다.
- 서버 환경 변수와 DB 스키마는 추가 없이 시작한다. `apps/web/.env.schema`의 `APP_MODE`는 배포 모드를 정하고 `BETTER_AUTH_URL`은 기존 인증 origin, `BETTER_AUTH_SECRET`과 공급자 키는 서버 비밀값, `OWNER_EMAILS`는 서버 소유자 판정에 쓰인다. CLI의 주소·로컬 세션 파일 경로는 CLI 로컬 설정이다. Vercel 배포·환경 변수 변경은 단계 검증 범위와 별개로 승인받는다. 업로드는 기존 WAV 검사와 배포에서 이미 검증한 본문 범위를 따른다. [Vercel Functions 제한](https://vercel.com/docs/functions/limitations)

## 유료 실행과 중단 복구

1. 모든 문단을 먼저 검증해 공급자별 한도와 파일 경로 오류를 찾는다. 같은 조합의 저장 결과, 새 요청 수와 예상 사용량을 보여 준다. 추정치가 없으면 그 상태를 그대로 표시한다. `plan`과 `--dry-run`의 비용 발생 호출은 0회다.
2. 과금 가능 작업은 대화형 확인 또는 `--yes`를 요구한다. 클론 생성은 `--consent`로 본인 음성 사용 동의를 별도로 받는다. 유료 자동 태그는 현재 서버의 묶음당 최대 호출 수를 확인문에 표시한다. 사용자가 `--yes`를 지정하지 않은 비대화 모드에서는 과금 가능 작업과 삭제를 중단한다.
3. 같은 origin·계정·요청 유형·정규화한 입력 지문을 동시에 실행하면 로컬 기록을 원자적으로 선점한 프로세스 한 개만 생성 요청을 보낸다. 이 프로세스는 문단별 요청 UUID와 전송 예정 상태를 디스크에 먼저 저장한다. 다른 프로세스와 이후 재개는 기록된 UUID로 상태를 조회한다. 문단은 서버의 동시 1건 제한을 그대로 적용해 순차 처리한다. 진행 기록에는 결과 ID·상태·문단 순번을 남긴다. 원문·오디오·세션은 각자의 기존 입력·출력·저장 경로에 둔다.
4. `studioFind/FindMany`와 `trialFind`는 새 생성 전 저장 결과 재사용에 쓴다. T20의 묶음 조회는 웹처럼 건수와 직렬화한 요청 바이트 한도로 나눈다. 자동 재개는 합성 요청을 보내지 않는다. T18은 세션 소유자와 작업 종류를 확인하는 읽기 전용 요청 UUID 상태 조회를 추가한다. 같은 조합의 다른 요청이 완료됐어도 UUID가 일치하는 결과만 해당 요청의 완료로 인정한다. 일치하는 기록이나 일부 응답이 없으면 미확인으로 남긴다. 시험 생성·드라마·클론도 확인 가능한 UUID나 이미 기록한 결과 ID가 있을 때만 완료로 연결하고, 확인 경로가 필요한 단계에서 같은 원칙으로 추가 범위를 정한다. 새 비용을 확인한 별도 생성만 새 UUID를 쓴다.
5. 묶음 재개에서 아직 전송하지 않은 문단의 실행은 별도 확인을 받는다. 중단 전 전송 대상으로 표시됐던 문단은 기록이 미확인이어도 자동 재전송 대상에서 제외한다. 자동 태그에는 생성 UUID 계약이 없으므로 같은 실행에서 네트워크 오류가 나도 CLI가 다시 요청하지 않는다.

각 단계의 실제 파일 목록과 테스트 명령은 그 Task가 열릴 때 확정한다. T18의 결과 메타데이터·요청 상태 조회는 `docs/domain/project.md`의 API 표에 반영한다. 패키지 단위 검사는 `pnpm --filter @tts-pilot-app/cli test`를 추가해 실행하고, 서버 계약 변경이 있는 단계는 기존 API 테스트와 소유자 격리 회귀를 함께 확인한다. 최종 확인은 CLI를 별도 프로세스로 실행해 종료 코드·stdout·stderr·파일 바이트를 검사한다. 자동화는 공급자 mock을 사용한다. 실제 과금·클론 상태 변경은 사용자가 승인한 호출만 확인한다.

초기 단계의 복구는 CLI 패키지 진입점이나 배포한 CLI 버전만 되돌리면 된다. CLI가 만든 작업실 데이터는 웹에서 기존 방식으로 계속 관리할 수 있다. 신규 API나 데이터 변경이 필요해지면 그 Task에서 기존 웹과의 호환성·되돌리기 절차까지 검토한다.
