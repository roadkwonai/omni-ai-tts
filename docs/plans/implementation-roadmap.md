## 1. 진행 방식

기능 하나를 화면·API·DB·공급자 연결까지 한 번에 완성한다. 기능이 앱에서 실제로 동작하고, 검증과 사용자 테스트를 통과해야 다음 기능으로 간다.

- **기존 계획과 다른 점:** [요구사항 6절](tts-service-requirements.md)과 [UI 우선 구현 계획](tts-ui-first-implementation.md)은 "화면 7개를 가상 데이터로 먼저 옮기고, 그 뒤에 데이터와 공급자를 붙인다"는 층별 순서였다. 이 로드맵이 그 순서를 대신한다. "UI/UX 먼저"라는 확정 사항은 HTML 시안(UI-01~10)으로 이미 채웠다. HTML은 앞으로도 각 기능의 화면 명세로 쓴다.
- **이유:** 층별 순서로 하면 공급자 연결 위험(유료 호출 중복, 오디오 4.5MB 한도, 계정 권한)을 맨 끝에야 알게 된다. 사용자가 실제로 써 볼 수 있는 기능도 끝까지 없다.
- **TASK 하나 = dev-cycle F 라운드 하나.** 라운드는 한 번에 하나만 열리므로(`pnpm dev-cycle status`) 순서가 도구로도 지켜진다.

## 2. TASK 게이트 (모든 TASK에 같은 절차)

| 단계 | 할 일 | 끝나는 조건 |
|---|---|---|
| 1. 설계 | `pnpm dev-cycle table F --write`로 라운드를 연다. `brainstorming`으로 스펙을 `docs/plans/tasks/Tnn-<이름>.md`에 쓴다. 스펙에는 범위와 제외, 화면과 상태, API, 데이터, 수용 기준, 자동 테스트 목록, **사용자 테스트 절차**를 넣는다. 화면이 있으면 impeccable `shape` 브리프를 `docs/briefs/`에 쓴다 | 사용자가 설계를 확인한다 |
| 2. 계획 | `writing-plans`로 `docs/plans/tasks/Tnn-<이름>-plan.md`를 쓰고 계획 리뷰를 받는다 | 리뷰 지적 처리 |
| 3. 구현 | 테스트 먼저(TDD), 계층 스킬(`bts-web`·`bts-ui`·`bts-api`·`bts-db`, 공급자는 `tts-provider`) | 대조표 구현 행 증거 |
| 4. 검증 | 타입·린트·테스트·빌드, 2계정 격리 테스트, `bts-reviewer`(code·security·db), impeccable critique·audit, 브라우저 1440·390 확인. 브라우저 QA에서 생성·시험 생성·클론·삭제 버튼은 누르지 않는다 | 대조표 검증 행 모두 증거 |
| 5. 사용자 테스트 | 스펙의 사용자 테스트 절차(주소, 계정, 순서, 기대 결과)를 드린다. 실제 유료 호출이 필요하면 공급자·모델·대본 길이·호출 횟수를 적어 승인을 먼저 받는다 | 사용자가 직접 써 본다 |
| 6. 피드백 반영 | 받은 피드백을 같은 라운드에서 고치고, 관련 검증을 다시 한 뒤 5로 돌아간다 | 사용자가 "통과"라고 한다 |
| 7. 닫기 | `[confirm]` 행에 사용자가 확인한 내용과 날짜를 적고 audit·close·커밋. 이 문서 3절과 `tasks/todo.md`의 TASK를 체크한다 | 커밋 |

- 앞 TASK가 7단계까지 끝나기 전에는 다음 TASK의 스펙·계획·코드를 만들지 않는다. 앞 TASK를 하다 다음 TASK에 필요한 사실을 알게 되면 이 문서 3절의 "설계 때 정할 것"에만 적는다.
- 사용자가 순서나 범위를 바꾸자고 하면 이 문서를 먼저 고치고 진행한다.
- TASK가 너무 커서 한 라운드로 끝내기 어려우면 설계 단계에서 Tnn-a, Tnn-b로 나누고, 나눈 TASK마다 같은 게이트를 거친다.

**TASK 완료 정의:** 스펙의 수용 기준마다 증거가 있다. 자동 테스트·타입·린트·빌드가 통과한다. 공급자 기능은 사용자가 승인한 실제 호출로 확인했거나, 계정 제한으로 확인하지 못했다고 적는다(그 공급자 기능은 미완료). `docs/domain/project.md`와 `CONTEXT.md`가 현재 모습과 맞다. 사용자 테스트와 피드백 반영이 끝났다.

**순서를 이렇게 정한 이유**
- T1이 먼저다. 가입이 열려 있고 소유자 검사가 없는 동안에는 공급자 키를 쓰는 기능을 붙일 수 없다(`tts-provider` 스킬).
- 공급자 하나(Typecast)로 "성우 고르기 → 생성 → 듣기·내려받기"를 먼저 끝까지 잇는다(T2·T3). 유료 호출의 중복 방지, 오류 매핑, 오디오 전달처럼 가장 위험한 부분을 일찍 확인하고, 사용자가 실제 작업에 쓸 수 있는 도구를 가장 빨리 갖게 된다. Typecast를 먼저 고른 이유는 목록에 페이지 나눔이 없어 가장 단순하기 때문이다.
- 숫자 교정(T4)은 공급자와 무관하고, 첫 생성 흐름에 바로 가치를 더한다.
- ElevenLabs(T5)와 Fish Audio(T6)는 T2·T3에서 만든 공통 계약에 붙인다.
- 즐겨찾기·분류(T7)는 세 공급자의 성우 식별(공급자 + 성우 ID)이 모두 있어야 한 번에 설계할 수 있다. 프리셋(T9)은 세 공급자의 설정 계약이 굳은 뒤에 저장 형식을 정한다.
- 클론(T10)은 가장 크고 공급자마다 계정 조건이 달라서 기반 기능 뒤에 둔다.
- 배포(T11)는 GitHub origin과 Vercel 연결, 운영 소유자 계정이 필요하다. 그 전 TASK의 사용자 테스트는 로컬 개발 서버에서 한다.

## 4. TASK별 범위

아래는 순서를 정하기 위한 범위다. 상세 설계는 그 TASK 차례가 왔을 때 게이트 1단계에서 한다.

### T1 앱 기반: 소유자 전용 로그인과 작업실 틀
- **포함:** 공개 가입 서버 차단과 가입 화면 제거. 소유자 허용 목록(서버 환경변수, 비어 있으면 모두 거부)을 `protectedProcedure`에 더한다. 로컬 DB에서만 동작하는 소유자 계정 준비 방법. 보호 레이아웃과 `/studio` 빈 작업실, `/dashboard` 정리. `DESIGN.md` 토큰을 `globals.css`로 옮기고 Pretendard와 `lang="ko"`를 적용. 테스트 러너(vitest)와 테스트 DB. 전체 Biome 오류 정리(Q-01, 이후 모든 라운드의 린트 행이 전체 검사로 통과하도록).
- **제외:** 성우, 대본, 생성(T2부터).
- **사용자 테스트:** 소유자 로그인 → 작업실 틀 진입, 가입 시도 거부, 허용 목록 밖 계정의 API 거부, 1440·390 화면.
- **설계 때 정할 것:** 소유자를 이메일로 허용할지 사용자 id로 허용할지, 소유자 계정을 만드는 방법, 아직 없는 화면을 내비게이션에 보일지.

### T2 Typecast 성우 찾기와 기본 샘플 듣기
- **포함:** 공급자 공통 계약(`packages/api/src/providers/contract.ts`)과 Typecast 목록·단건 조회. 공급자 연결 상태(키가 없으면 "연결 안 됨"). 성우 선택 화면(검색, 모델·성별·연령·용도 필터, 샘플 없음 표시). 한 번에 하나만 재생. 무료 호출만 쓴다.
- **사용자 테스트:** 성우 검색·필터, 샘플 청취, 작업 성우 선택, 키가 없을 때의 표시.
- **설계 때 정할 것:** 성우 선택을 작업실 드로어로 할지 캐스팅 페이지로 할지, 목록을 서버에서 얼마나 캐시할지.

### T3 Typecast 음성 생성·재생·다운로드
- **포함:** 작업실 대본 입력(초안 유지), 빈 값·2,000자 상한 검사. Typecast 모델별 설정(옵션 매핑표 기준). 생성 기록 테이블(요청 id 선점, 사용자별 동시 1건). 호출마다 하는 소유자 검사. 공급자 오류 매핑과 "처리 여부 미확인". 예상 사용량(글자 수). 결과 재생·다운로드(다운로드가 생성을 다시 부르지 않음), 이전 결과 표시, 파일 이름.
- **사용자 테스트:** 짧은 대본으로 실제 생성 1회(승인 후), 재생·다운로드, 빈 대본·상한 초과 차단, 두 번 눌러도 요청 1회.
- **설계 때 정할 것:** 대본 입력을 HTML 작업실처럼 문단 카드 1장으로 시작할지 단일 편집기로 할지, 오디오 전달 방식(4.5MB 한도), 브라우저 QA에 쓸 모의 모드가 필요한지, 일일 사용 한도.

### T4 한국어 숫자 발음 교정
- **포함:** 규칙 기반 교정 엔진과 [요구사항 5절](tts-service-requirements.md) 수용표 전체의 자동 테스트. 원문과 발음용 대본 분리, 항목별 적용·유지·직접 수정·되돌리기, 원문을 고치면 재검수, 미검수 경고, 교정 후 길이 재계산, 발음용 대본 복사.
- **사용자 테스트:** 수용표 예시가 든 대본을 검수하고, 원하면 생성해 듣는다.
- **설계 때 정할 것:** Typecast AutoTag 채택 여부(P0-12 평가).

### T5 ElevenLabs 연결
- **포함:** 계정 성우와 공개 Voice Library(페이지 탐색), 샘플, 모델별 설정, 생성(SDK 자동 재시도 끔). 공개 성우를 판정할 필드를 공식 문서로 확인해 research 문서에 적는다.
- **사용자 테스트:** 공개 라이브러리 3페이지 이상 탐색, 샘플, 실제 생성 1회(승인 후), 공급자를 바꿀 때 맞지 않는 옵션 초기화.

### T6 Fish Audio 연결
- **포함:** 공개·내 성우 목록(페이지), 샘플, `model` 헤더로 합성 모델 선택, prosody·temperature·형식, 인라인 감정 태그, UTF-8 바이트 사용량, 생성.
- **사용자 테스트:** 목록·샘플, 실제 생성 1회(승인 후), 바이트 기준 예상 사용량.

### T7 성우 보관함: 즐겨찾기·자주 사용·채널/카테고리/타입
- **포함:** 개인 성우 설정과 분류 테이블, CRUD, 2계정 격리. 성우 선택 화면의 보기(즐겨찾기·자주 사용·최근 사용). 분류 편집 패널과 항목 관리. 성공한 생성 기록으로 최근 사용·횟수 계산. 공급자 목록에서 사라진 성우의 "현재 이용 불가" 표시.
- **사용자 테스트:** 세 공급자 성우를 즐겨찾기·분류하고 다시 로그인해 확인, 분류를 지우면 연결만 풀리는지 확인.

### T8 대본 보관함
- **포함:** 저장·수정·복제·삭제·검색, 작업실 삽입·교체, 저장 안 된 편집 경고, 동시 편집 충돌(버전 조건 갱신). 저장 상한(Q-02)을 설계 때 정한다.
- **사용자 테스트:** 대본을 저장하고 불러와 편집해도 원본이 바뀌지 않는지, 미저장 경고.

### T9 프리셋과 채널 기본값
- **포함:** 공급자별 유효 설정 저장·수정·복제·삭제, 채널 기본 프리셋, 적용 전 바뀌는 값 비교, 성우·모델을 쓸 수 없게 되면 다시 고르게 함.
- **사용자 테스트:** 프리셋 저장 → 새 작업에 적용 → 같은 설정으로 생성.

### T10 내 보이스(클론)
