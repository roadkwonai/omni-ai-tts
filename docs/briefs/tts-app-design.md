## 1. 목표와 완료 기준

사용자가 저장한 성우·대본·프리셋을 다시 찾아, 숫자 발음을 검수하고 실제 한국어 음성을 내려받을 수 있어야 한다. 기존 HTML의 화면 구성을 유지하면서 시연 데이터와 실제 동작을 구분한다.

첫 출시 완료는 양사 각각의 **성우 탐색 → 샘플 청취 → 대본 저장 → 교정 검수 → 생성 → 재생·다운로드**, 개인 분류의 재로그인 복원, 본인 간편 클론의 생성·사용·삭제로 판정한다. 계정 권한 때문에 검증하지 못한 공급자는 미검증으로 남긴다. 화면만 옮긴 상태는 출시 완료가 아니다.

| 구분 | 범위 |
|---|---|
| 기존 확정 사항 | 개인용, 서버 환경변수의 공급자 키, Typecast·ElevenLabs, Wanted 스타일, 로컬 Pretendard, 기존 BTS 구조 |
| 이번 설계 제안 | 7개 화면과 작업실 중심 구성 유지, 단계별 앱 이관, 현재 세션의 초안 보존, 생성 기록과 임시 오디오 분리 |
| 이번에 결정하지 않는 것 | 오디오 영구 보관 서비스·기간, 공개 가입·결제·팀, 추천 품질 알고리즘, 영상·자막 편집 |

### 작업실 구성

```text
PC:   내비게이션 | 작업명·채널·저장 상태·프리셋·음성 만들기
                 | 여섯 제작 도구 — 기존 이름과 그룹 유지
                 | 성우 선택 패널 | 선택 성우·모델·접는 설정
                 |               | 원문 / 발음용 대본·검수
                 |               | 결과 재생·다운로드
모바일: 메뉴·작업 요약 → 제작 도구 → 성우/대본/설정 전환 → 생성 행동
```

- 대본 편집면을 가장 넓게 둔다. 설정을 독립된 상시 3번째 작업 패널로 확장하지 않는다.
- 즐겨찾기는 기존 사용자 지정 **노란 채움 별 / 회색 윤곽 별**을 유지한다. 샘플 청취·선택·즐겨찾기·자주 사용은 독립 행동이다.
- 도구 패널을 닫으면 대본으로 돌아오고 초안은 유지한다. 복제는 내 보이스로 이동하고 작업실 복귀를 제공한다.
- 1440·1024·390px를 검증 기준으로 삼는다. 모바일에서 여섯 도구 이름과 생성 상태를 읽을 수 있어야 한다.
- 기존 shadcn과 CSS 토큰을 재사용한다. 키보드 조작·모달 포커스 복귀·상태 알림·44px 터치 영역을 수용 기준에 포함한다.

## 4. 핵심 사용자 흐름

### 반복 제작

1. 채널 또는 프리셋 선택 → 적용할 성우·모델·설정을 확인한다. 현재 대본은 바꾸지 않는다.
2. 성우 탐색 → 기본 샘플 청취 → 선택. 샘플이 없으면 이를 표시하고 시험 생성을 별도 행동으로 제공한다.
3. 대본 작성 또는 불러오기 → 삽입/교체 선택. 편집한 저장 대본은 명시적으로 저장하기 전 원본을 갱신하지 않는다.
4. 숫자 후보를 적용·유지·직접 수정 → 미검수 0건과 최종 생성문 확인. 원문 변경 시 이전 검수는 무효화한다.
5. 모델 설정·글자 수·사용량 확인 → 명시적으로 생성. 과금 추정 근거가 없으면 금액을 만들어 표시하지 않는다.
6. 결과 청취·다운로드. 생성 후 입력을 바꾸면 이전 결과임을 표시하고 기존 결과는 유지한다.

### 개인 정리

성우 행의 분류 편집 → 채널·카테고리·타입 다중 선택 → 저장 성공 후 목록·필터 반영. 동일 그룹은 OR, 그룹 사이는 AND다. 분류 취소는 성우 연결을 취소하며, 패널에서 새 항목 만들기는 별도 저장 행동임을 알린다. 즐겨찾기와 자주 사용은 서로 독립한다.

### 내 보이스

공급자·이름 → 파일/녹음 → 원본 청취·본인 음성 동의 → 전송 → 검증 필요/사용 가능 → 별도 시험 생성 → 작업실 사용. 원본 재생을 클론 합성 결과로 표시하지 않는다. 삭제 전 연결 프리셋을 보여 주고, 삭제가 확인된 성우는 선택을 막는다. 향후 문단 계획에서도 같은 차단 규칙을 적용한다.

**원본 취급 제안:** P0 서버는 원본을 DB·디스크·영구 저장소에 저장하지 않고 인증된 요청 안에서 제한된 메모리/스트림으로 공급자에 전송한다. 요청별 전송 시간은 최대 120초로 제안하며, 이는 공급자의 클론 처리 완료 시간 보장이 아니다. 성공·실패·취소·연결 종료·시간 초과 모두에서 스트림을 닫고 버퍼 참조를 해제한다. 중단이 공급자 처리를 취소했다는 뜻은 아니므로 결과가 불명확하면 ‘처리 여부 미확인’으로 남긴다. 원본 조회 URL이나 요청 본문 로그를 만들지 않고, 전송 전 소유자·동의·형식·용량을 서버에서 검증한다. 브라우저 원본 URL은 재선택·취소·화면 이탈 때 폐기하고 마이크 트랙도 종료한다.

실제 SDK나 변환기가 디스크 임시 파일을 요구하면 이 메모리 전용 안을 충족하지 못한다. 그 구현에 들어가기 전에 별도 보관 설계를 확정해야 하며 임시 저장을 조용히 추가하지 않는다. 공급자 측 원본 보관·삭제는 앱 메모리 정리와 별개다. 각 공급자 연동 전에 공식 정책과 계정 조건을 확인해 전송 전 안내에 반영하며, 확인하지 못한 경우 해당 클론의 실전송을 활성화하지 않는다.

## 5. 상태와 데이터 손실 방지 계약

| 상황 | 설계 규칙 |
|---|---|
| 새 작업 | 저장 이력이 없으면 ‘저장됨’을 표시하지 않는다. 비어 있는 성우·대본에 다음 행동을 제공한다 |
| 내부 화면 이동 | 공유 보호 레이아웃 아래 작업실 초안을 유지한다. 필터는 URL, 편집 중 대본은 URL에 넣지 않는다 |
| 새로고침·창 닫기 | P0는 자동 복구를 보장하지 않는다. 미저장 시 이탈 경고와 명시적 대본 저장을 제공한다. 브라우저 경고에만 의존하지 않는다 |
| 저장 실패·세션 만료 | 편집 내용을 화면에 유지하고 재시도·복사 경로를 제공한다. 실패 응답을 저장 성공으로 표시하지 않는다 |
| 교정 상태 | 원문 버전과 범위를 가진 후보를 검수한다. 원문을 고치면 재검수. 제안이 0건인 상태와 분석 실패를 구분한다 |
| 길이 정책 | 생성문 2,000자는 기존 제품 제안 상한이다. 공급자/모델의 더 낮은 한도와 교정·연출 태그 적용 후 실제 입력을 서버에서 다시 검사한다 |
| 저장 대본 크기 | 가져오기의 200,000자·200문단을 P0 저장 상한으로 자동 채택하지 않는다. 저장 한도와 생성 한도는 구분하며 구현 전 Q-02에서 일관된 값을 정한다 |
| 프리셋 비호환 | 모델·성우가 사라지거나 옵션이 유효하지 않으면 표시하고 재선택을 요구한다. 다른 모델로 조용히 대체하지 않는다 |
| 카탈로그 지연·부분 실패 | 공급자별 오류·검색 범위를 표시한다. 필터 변경 전 늦은 응답을 현재 목록에 합치지 않는다 |
| 생성 진행 | 요청 시작 시 입력을 고정한다. 중복 클릭을 막고 임의 완료 퍼센트는 표시하지 않는다 |
| 응답 유실 | ‘생성 여부 미확인’으로 남긴다. 자동 재생성하지 않고 추가 사용량 가능성을 표시한다 |
| 결과 만료 | 생성 기록은 남아도 임시 오디오는 만료될 수 있다. 재다운로드 불가와 새 생성 행동을 구분한다 |

## 6. 앱 구조와 데이터 경계 제안

기존 Next.js → oRPC → Drizzle/Postgres 경계를 유지한다. 브라우저는 공급자 키를 갖지 않고 API는 세션 소유자·입력·성우 이용 가능 여부·모델 옵션을 다시 검사한다. 화면 보호만으로 API 보호를 대신하지 않는다.

- **앱 화면:** `apps/web/src/app`의 공통 보호 레이아웃과 `features/tts`의 화면 단위 컴포넌트. React 지역 상태로 편집 초안을, 기존 TanStack Query로 서버 데이터를 관리한다. 전역 상태 라이브러리 추가는 전제하지 않는다.
- **API:** `packages/api` 안에서 성우 조회, 개인 저장, 생성, 클론의 책임을 나눈다. 공급자별 구체 함수와 입출력 타입을 먼저 두고 범용 플러그인 체계는 만들지 않는다.
- **DB:** 현재 인증 테이블에 필요한 개인 데이터만 추가한다. 아래는 논리 엔터티이며 SQL·마이그레이션 확정안은 아니다.

| 데이터 | 최소 책임과 식별 경계 |
|---|---|
| 개인 성우 정보 | userId + provider + voiceId, 즐겨찾기·자주 사용·메모. 공급자 카탈로그 전체 복제는 하지 않음 |
| 채널·카테고리·타입 및 연결 | 이름과 분리된 고정 ID, 소유자, 종류별 중복 이름 정책. 연결 대상과 소유자 일치 검사 |
| 저장 대본 | 소유자, 제목·원문, 채널·분류. 작업실 초안과 분리 |
| 프리셋 | 소유자, 성우·모델·유효 설정·교정 모드, 선택 채널. 설정은 공급자별 검증된 구조로 저장 |
| 생성 기록 | 소유자·요청 ID, 원문/발음용 대본·설정 snapshot, 처리 상태·공급자 요청 ID·확인 가능한 사용량 |
| 내 보이스 | 소유자·공급자·voiceId, 이름·동의 기록·검증/삭제 상태. 실제 사용 가능 여부와 연동 |

개인 데이터 프로시저는 `protectedProcedure`를 쓰고 userId를 입력받지 않는다. 연결·삭제·합성에서 참조 대상의 소유권도 확인한다. 최근 사용·횟수는 성공한 생성 기록에서 계산하고 샘플 재생은 집계하지 않는다.

### 유료 생성과 결과 처리

1. 클라이언트 요청 ID와 입력 snapshot을 받아 서버에서 유효성·소유권을 검증한다.
2. DB의 소유자+요청 ID 고유 제약으로 중복 요청을 식별한다. 같은 ID에 다른 입력이면 거절한다.
3. 공급자 요청 전에 처리 중 기록을 남기고 외부 호출 중 DB 트랜잭션을 유지하지 않는다. 같은 요청 ID의 재전송은 기존 상태만 반환한다.
4. 성공·명확한 실패·처리 여부 미확인을 분리한다. 공급자 idempotency나 조회 지원은 연동 시 확인하고 지원을 가정하지 않는다.
5. 초기 결과는 인증된 응답으로 받은 오디오를 현재 브라우저 세션에서 재생·다운로드하는 안이다. Blob URL을 영구 URL로 DB에 저장하지 않는다. 서버 기록만 남고 결과가 전달되지 못했다면 재다운로드를 보장하지 않는다.

별도 큐·워커·오디오 저장소는 선행 도입하지 않는다. 실제 응답 시간·배포 제한 확인 결과로 요청 안에서 완료할 수 없다면 해당 생성 단계의 작업 실행 방식을 별도 결정한다. 영구 결과 보관은 기존 P1-02에서 저장소·기간을 정한 뒤 도입한다.

## 8. 설계 검토에서 확정할 항목

1. 기존 P0 우선순위를 유지할지, 여섯 제작 도구의 실연동까지 첫 출시로 올릴지. 후자를 고르면 파일 파싱·문단 모델·분석·변환 검증이 초기 범위에 추가된다.
2. 오디오는 기존 제품 맥락의 최소 보장인 현재 세션 재생·다운로드를 적용한다는 제안. 영구 보관 필요 시 P1-02를 앞당겨야 한다.
3. 구현 직전 확정할 수치: 대본 저장/편집 상한(Q-02), 공급자별 실제 글자/파일 제한, 계정별 클론 지원. 현재 외부 API 동작이나 계정 지원을 재검증한 문서는 아니다.

이 문서 작성은 설계안 준비 완료를 뜻한다. P0-03의 브리프 확정과 실제 앱 기능 완료 체크는 사용자 검토 및 해당 검증 뒤에만 갱신한다.

#### 4. 데이터·상호작용

검색→필터→늦은 응답과 생성→입력 변경→늦은 결과가 대표적인 순서 문제다. 단순 버튼 비활성은 다른 탭이나 서버 재시작을 막지 못한다. DB 요청 ID 제약과 query key·원문 버전을 역할에 맞게 사용하고, 완료 순서를 뒤집는 테스트를 요구한다(C06).

```text

      nil=기본필터 / empty=0건 / upstream=해당 공급자 오류
저장: 제목·원문 -> 검증 -> 소유자 DB -> 저장 버전
      nil·empty=거절 / DB실패=초안 유지 / stale=새 편집을 저장됨으로 표시 금지

      nil·empty=생성 불가 / 분석실패=원문 유지 선택 / stale=재검수
생성: 요청ID·snapshot -> 권한·한도 -> DB기록 -> 공급자 -> 오디오
      nil·empty=호출0 / timeout=미확인 / empty audio=실패
클론: 동의·원본 -> 형식·소유자 -> 전송 -> 공급자 상태 -> ready
      nil·empty=전송0 / timeout=미확인 / 삭제중=선택 불가

시간   조회A            조회B              현재 필터
 t1    A 시작                              A

 t3    A 완료(폐기)                         B
 t4                     B 완료(표시)       B
 역순: B 완료 후 A 완료도 A 폐기. query key/요청세대로 보장.

시간   생성G(snapshot v1)  편집v2           결과 소유 입력
 t1    G 시작                              v1
 t2                       원문 변경        v1
 t3    G 완료                              v1(이전 결과)
 역순: G 완료 후 v2 변경도 동일하게 이전 결과 표시.
```

상태 기계: `편집→검수→준비→요청중→성공/실패/미확인`; 원문 변경은 검수를 무효화하며 성공 결과를 수정하지 않는다. 클론은 `입력→전송→처리→검증필요/ready/실패/미확인→삭제중→삭제/삭제실패`이며 ready 외 생성 선택은 막는다. 생성 미확인을 준비 상태로 자동 되돌리는 전이는 금지한다.

#### 5. 코드 품질

프로토타입의 전역 DOM 브리지와 모의 공급자 응답을 실제 앱 구조로 복사하지 않는다. `features/tts` 안 화면 컴포넌트와 검수 순수 함수, 공급자별 작은 함수로 나누는 현재 방향을 유지한다. 기존 함수가 없는 영역만 만들고 범용 플러그인·두 번째 상태관리·인증 체계를 추가하지 않는다(C07).

#### 6. 테스트

현재 package.json과 파일 목록에서 제품 테스트를 확인하지 못했다. 기존 계획의 검증 문장은 실행 가능한 테스트가 아니므로 신규 UX·데이터·유료 요청의 정상/실패/경계를 구분한 목록이 필요하다. 각 테스트는 결과뿐 아니라 공급자 호출 횟수·다른 사용자 DB 불변을 단언해야 한다(C06).

```text
새 UX     로그인/7화면/복귀/저장/검수/생성/다운로드/클론 -> E2E
새 데이터 소유권 CRUD/연결/프리셋/생성기록 -> DB 통합
순수 분기 null/공백/초과/검수버전/옵션부적합 -> 단위
비동기    늦은목록/저장중편집/생성중편집/중복ID/삭제충돌 -> 제어된 통합
외부      목록/TTS/클론의 401·429·timeout·빈응답 -> 가짜 공급자
실음질    숫자 유형별 원문/교정문과 양사 결과 비교 -> 사용자 청취
```

기존 필수 숫자 유형을 실제 표본에 없다는 이유로 삭제하지 않는다. 날짜·금액·소수·퍼센트·전화번호·단위·고유어 수사의 회귀 세트와 대표 대본 3–5개로 오류·수정량을 측정한다(C02). 현재 P0에 LLM 추천 프롬프트는 없으므로 LLM eval은 해당 없음; 추천·감정 분석 승격 시 별도 품질 평가가 필요하다.

#### 7. 성능

가장 느릴 경로는 공급자 TTS, 원본 전송, 계정/공개 카탈로그다. 실제 p95/p99 수치는 측정 전이라 제시하지 않는다. 전체 카탈로그 선적재·사용자별 메모의 행별 조회·원본 무제한 buffering을 금지하고 크기·동시성·페이지 범위를 구현 전 준비 표에 넣는다(C01, C05).

#### 8. 운영 관측

실패 시 대본이나 원본을 로그에 넣지 않고도 requestId·공급자·모델·상태·경과 시간·바이트 수·오류 코드로 조사할 수 있어야 한다. 최소 로그와 요청 기록은 필요하지만 별도 대시보드·알림 서비스는 개인용 P0에 도입하지 않는다. 상태 미확인 시 외부 기록 확인→가능하면 조회→사용자가 별도 재생성을 선택하는 복구 절차를 적는다(C06).

#### 9. 배포·되돌리기

배포는 이번 작업의 실행 범위가 아니지만 설계에는 순서가 필요하다. additive migration을 로컬 전용 테스트 DB와 Neon 개발 브랜치에서 확인한 뒤 앱을 배포하고, 연결 준비가 안 된 공급자는 서버에서도 유료 동작을 차단한다. 문제가 나면 유료 기능을 닫고 앱 버전을 되돌리며, 사용자 데이터 테이블을 삭제해 롤백하지 않는다(C08).

```text
테스트DB migration -> 격리/회귀 -> Neon 개발검증 -> 앱 배포 승인
 -> 소유자 로그인 -> 비과금 조회 smoke -> 승인된 실제 생성 검증
실패 -> 신규 유료 호출 차단 -> 기존 기록 보존 -> 앱 rollback -> 원인 확인
```

#### 10. 장기 방향

양사 voiceRef·snapshot과 개인 데이터 경계는 문단 제작으로 확장할 수 있다. 세션 결과와 저장 대본을 프로젝트처럼 보장하지 않는 점도 명확하다. 변경 가능성은 4/5이며, 되돌리기 어려운 선택은 실제 공급자에 전송한 원본·발생한 비용이라서 공급자 정책과 사용자 행동에 연결한다.

#### 11. UI/UX

기존 HTML은 대본과 검수 중심의 구체적인 구조이며 일반 대시보드 템플릿을 새로 만들 필요가 없다. 가장 큰 UX 위험은 상시 도구 중 미연동 기능이 실제 기능처럼 보이는 것과 첫 대본의 ‘저장됨’ 표시다. 실제 지원 여부·저장 성공 조건·복귀 동작을 유지하고 세부 화면별 상태는 다음 Design 단계에서 검토한다.

| 기능 | Loading | Empty | Error | Success | Partial |
|---|---|---|---|---|---|
| 성우 | 공급자별 로딩 | 검색/보관 없음 구분 | 공급자 오류 | 선택·샘플 | 일부 공급자/페이지 실패 |
| 대본 | 불러오는 중 | 첫 대본 | 저장 실패·초안 유지 | 저장 버전 | 저장 중 추가 편집 |

DB 마이그레이션을 적용할 때에는 로컬과 Neon 중 어디를 향하는지 확신하고 싶다. 잘못된 연결 문자열로 데이터를 바꿀 생각은 없다. 앱을 실행한 다음에는 처음 로그인할 계정을 어떻게 만들지 궁금해진다. 공개 가입을 닫겠다는 설계와 첫 계정 준비를 동시에 이해해야 한다. 공급자 키를 넣기 전에는 무료로 상태와 오류를 확인하고 싶다. 키를 넣은 순간 버튼이 실제 비용을 발생시키는지도 분명해야 한다. 내가 원하는 것은 새 설정 마법사가 아니라 시작 순서가 있는 짧은 문서다. 생성 오류가 나면 영어 원문과 retry 토스트만 보는 대신 요청 번호와 해결 행동을 찾고 싶다. 며칠 뒤 모델을 바꿔도 예전 프리셋이 조용히 다른 목소리로 생성되지 않아야 한다. 코드 타입과 작은 테스트 대역이 이 차이를 보여 주면 안심할 수 있다. 이 서술은 README와 코드에 근거한 역할 시뮬레이션이며 실제 설치 시간이나 사용자의 관찰 기록은 아니다.

#### 0G. 처음 실행 혼동 로그(시뮬레이션)

T+0:00 README의 HTML/실서비스 구분 확인. T+0:30 설치 명령을 찾지만 DB 컨테이너 시작은 package.json을 열어야 한다. T+1:00 환경 예시를 찾은 뒤 비밀값·포트·대상 DB를 확인한다. T+2:00 신규 DB의 소유자 준비 절차에서 막힌다. T+3:00 모의 모드와 실연동 모드의 명시적 설정이 없어 유료 호출 여부를 확신하지 못한다. 이는 현재 명령을 실행해 얻은 시간이 아니라 문서 혼동 지점의 순서다.

#### Pass 1 시작하기 — 4 → 8

README와 .env.example, package.json에는 이미 설치·환경 예시·DB·dev 명령이 존재한다. 전부 재작성하는 대신 README 상단에 연결하고 로컬 소유자 생성 방법을 추가하면 된다. 환경을 덮어쓰거나 공개 가입을 잠시 여는 방식은 피하고, bootstrap은 명시한 로컬 DB에서만 동작하는 한 번의 작업으로 설계한다(X01).

구현 후 문서에 들어갈 검증 순서는 다음이다. 현재 아직 없는 소유자 bootstrap은 아래에서 명확히 계획으로 표기한다.

```text
전제 확인: 저장소의 Node/패키지 매니저 버전, 실행 중인 Docker/Podman
1. pnpm install --frozen-lockfile
2. apps/web/.env.example 기준으로 없는 환경값 준비(기존 .env 덮어쓰기 금지)
3. pnpm db:start -> pnpm db:migrate (명시적으로 로컬 대상 확인)
4. 로컬 소유자 bootstrap [신규 구현 필요] -> OWNER_USER_ID 확인
5. pnpm dev -> http://localhost:3001 -> 로그인 -> /studio의 모의 표시
```

다운로드까지 포함한 3단계/5분을 보장하려고 전용 setup CLI를 만들지 않는다. 실행 횟수보다 안전한 DB 대상·과금 상태가 먼저다.

#### Pass 2 API·설정 — 5 → 8

oRPC 타입과 queryOptions/mutationOptions는 이미 코드에 있다. provider+voiceId, requestId와 snapshot이 무엇을 의미하는지 한 예제에서 설명하고 고급 옵션은 공급자별 검증 타입으로 한정한다(X03). UI 페이지 크기까지 환경변수로 만드는 제안은 기각하고 운영상 바뀌는 키·활성 상태·한도만 설정으로 둔다.

| 값 | 관리 위치 / 단위 | 규칙 |
|---|---|---|
| 소유자 | 서버 OWNER_USER_ID | 로컬 bootstrap으로 확인, 웹 요청으로 설정 불가 |

#### Pass 3 오류 — 5 → 8

`utils/orpc.ts`의 전역 `Error: message`와 `retry`는 개인 작업실의 인라인 오류와 중복될 수 있다. 원문 서버 메시지를 그대로 보여 주지 않고 안전한 앱 코드·필드·requestId·도움말 앵커를 전달한다(X04). 실제 정책은 Eng에서 읽기 재시도와 유료 요청 재시도를 구분한다.

| 경로 | 현재 근거 | 계획의 사용자/개발자 대응 |
|---|---|---|
| 세션 없음 | protectedProcedure UNAUTHORIZED | ‘로그인이 만료됐어요’ / 초안 복사·다시 로그인 / README 인증 절 |
| 키·권한·한도 | 아직 제품 오류 없음 | 연결 상태의 해당 공급자·원인·수정 방법 / requestId / 공식 문서 |
| 유료 응답 유실 | 계획 상태만 존재 | ‘생성 여부를 확인하지 못했어요’ / 상태·공급자 확인, 자동 retry 없음 / 기록 ID |

내부 스택·키·대본·원본은 도움말 URL이나 JSON 응답에 넣지 않는다. 구체적인 HTTP/SDK 원인을 사용자 문구로 번역하되 정보가 없는 원인을 확정하지 않는다.

#### Pass 4 문서 — 5 → 8

README와 많은 기획 문서를 읽어야 시작할 수 있으면 개발자가 정본을 고르느라 시간을 쓴다. README를 실행 진입점으로 두고 제품 용어 GLOSSARY.md, 현재 구현 docs/domain/project.md, 이번 설계안, 공급자 옵션 문서로 역할을 나눈다(X01/X03). 5개의 새 docs/tts 파일을 자동 추가하는 제안은 중복이라 기각한다.

#### Pass 5 업그레이드 — 5 → 8

Drizzle ORM/catalog와 kit 버전은 lockfile의 실제 조합을 기록해야 한다. 모델 지원 변경은 프리셋을 조용히 변환하지 않고 다시 선택하게 하며, 마이그레이션은 이전 앱과 공존하는 추가형을 기본으로 한다(X05). 공개 SDK가 아니므로 semver 서비스·자동 codemod 체계는 새로 만들지 않는다.

#### Pass 6 환경·검증 — 5 → 8

루트 check는 쓰기 명령이고 읽기 전용 검사는 `pnpm exec biome check .`이므로 문서에 차이를 표시한다. 기존 스크립트 이름을 바꾸는 것은 이번 TTS 검토에 불필요하며 관련 CLI 사용처를 깨뜨릴 수 있다. test runner·전용 TEST_DATABASE_URL·가짜 공급자는 첫 서버/DB 구현 라운드에서 준비하고, mock/live 분기에서도 소유자 검사와 입력 검증을 건너뛰지 않는다(X02/X06).

#### Pass 7 생태계 — 8 → 8

이 저장소는 개인 앱이고 공개 SDK 배포나 기여자 모집을 요구하지 않는다. 따라서 커뮤니티 채널·다국어 SDK·플러그인 생태계를 만드는 것은 범위 밖이다. 유지보수 관점에서는 기존 README, lockfile, 코드 소유권, 의존성 라이선스 기록을 사용하면 충분하며 새 작업은 없다.

#### Pass 8 측정 — 3 → 8

현재 첫 실행 시간의 실측은 없고 이를 이미 5분이라고 주장할 수 없다. 구현 후 깨끗한 로컬 테스트 환경에서 준비된 의존성 기준 실행 시간, 명령 수, 오류 위치와 복구 시간을 한 번 기록한다(X06). 과금과 상관없는 개발환경 측정에 원격 사용자 분석 시스템을 추가하지 않는다.

##### E01. 한도와 동일 요청

[Layer 1] 프로세스 전역 mutex 대신 DB의 소유자 `user` 행을 FOR UPDATE로 잠근다. 인증 테이블을 변경하지 않으며 이 잠금의 목적은 짧은 비용 예약 구간 직렬화다. 잠금 순서는 소유자→참조 클론→요청으로 통일하고 외부 호출 동안 유지하지 않는다. 환경에서 정한 동시 한도 N도 이 하나의 경로에서 검사한다; 외부의 동시1 고정 제안은 기존 설정 계약을 축소하므로 채택하지 않는다.

```text
두 탭 A / B                 소유자 잠금 + 요청 기록
A 잠금 획득                 B 대기
A 동일ID 확인·한도검사
A 예약·요청INSERT·COMMIT     잠금 해제
B 잠금 획득                 A 예약을 포함해 한도검사
B 같은ID -> 기존상태        새 공급자 호출0
B 다른ID·초과 -> 거절       초과 공급자 호출0
```

반대 순서로 B가 먼저 잠가도 같은 성질이 성립한다. 서버가 검증·정규화한 provider/voiceId/model/최종 대본/설정/종류를 고정 순서로 직렬화해 SHA-256을 저장한다. 같은 ID·같은 해시는 기존 상태를, 같은 ID·다른 해시는 CONFLICT를 반환한다. 요청 ID가 다르면 의도적인 새 생성일 수 있으므로 텍스트 해시만으로 과금을 생략하지 않는다.

일일 한도는 Asia/Seoul 자정 기준 예약일과 서버의 최종 입력 글자 수·요청 건수를 사용한다. 유료 시험 생성도 포함하고 클론은 요청 건수에 포함하되 text chars=0이다. 공급자 실사용량은 별도 참고 필드이며 unknown도 예약을 유지한다. 호출 전에 실패한 것이 입증될 때만 예약을 해제한다. 이것은 결제 원장이 아니라 앱의 보수적 요청 제한이다.

##### E02. 처리 중·미확인·결과

```text
검증 -> reserved+dispatchDeadline -> 공급자 전송
        | 호출 전 실패 확정        | 응답·DB 갱신 성공
        v                         v
     failed(예약해제)        providerSucceeded
                                  ├ audioAvailable(현재 브라우저)
                                  └ audioUnavailable(전달/세션 유실)
        전송 후 불명 / crash -> unknown(일일예약 유지)
```

동시 한도는 현재 서버의 유료 전송/응답 처리 구간에 적용하며 공급자의 클론 학습 완료까지 잠그지 않는다. 서버 실행이 끝났음을 판단할 수 있는 검증된 호스트 최대 실행 시간+여유 이후에만 stale dispatch 슬롯을 조건부 해제한다. 호스트의 종료 상한을 입증할 수 없으면 임의로 슬롯을 재사용하지 않고 소유자가 실행 종료를 확인하도록 한다. 상태 조회는 공급자의 공식 지원 여부에 따라 수행하고, 새 생성으로 복구하지 않는다.

provider 성공 뒤 DB 기록 실패도 자동 재호출하지 않는다. 클라이언트가 오디오를 받았으면 현재 세션 다운로드는 유지하되 ‘기록 확인 필요’라고 표시하고, DB의 unknown을 성공으로 위장하지 않는다. 클론 응답 유실은 공급자 request ID 등 검증 가능한 식별자로만 대조하며 이름이 비슷하다는 이유로 소유권을 인계하지 않는다. 원본이나 결과 바이너리를 에러 로그로 복구하려 하지 않는다.

##### E03. 업로드·호스트 한도

원본은 인증·소유자·동의 확인 후에만 읽고, 헤더의 길이가 있으면 먼저 거절하며 실제 스트림 바이트 수도 제한한다. 길이 헤더가 없다고 무제한 읽지 않으며 유효한 chunked 입력은 바이트 상한으로 처리할 수 있다. 파일명/MIME만 믿지 않고 실제 컨테이너·오디오 길이·허용 형식을 검증한다. 전체 검증이 필요한 형식은 **유한 크기의 메모리 버퍼** 안에서 검사한 뒤 공급자에 보내고 디스크에는 쓰지 않는다.

120초 제안보다 호스트 제한이 짧으면 더 짧은 한도를 쓰고, 수신·검증·공급자 전송·응답/중단 각 시간 예산을 준비 표에 기록한다. 입력 문자 수로 실제 음성 시간을 정확히 예측할 수 없으므로 외부의 ‘호스트 바이트/비트레이트로 생성문자 한도 도출’ 공식은 채택하지 않는다. 실제 최대 입력·형식의 응답 크기/시간과 스트리밍 동작을 해당 배포 환경에서 검증하고, 전송 보장을 입증하지 못하면 live를 열지 않는다. queue/저장소가 필요하다는 결론이 나오면 사용자에게 범위 변경으로 제시한다.

##### E04. 초안·저장 경쟁

초안·검수·현재 Blob은 개별 `/studio` 페이지가 아니라 내부 이동에도 유지되는 공유 client provider에서 관리한다. 새 전역 상태 라이브러리는 필요 없다. 보호 서버 페이지의 직접 진입 검사는 유지하되 이미 열린 작업 중 세션이 만료되면 요청 실패를 인라인 처리하고 먼저 복사/재로그인 행동을 제공한다. 로그인 탭을 별도로 열어 같은 편집 페이지를 보존할 수 있다.

```text
클라이언트 revision 4 -> 저장A(expected DB version 8)
사용자 편집 revision 5
저장A 완료 DB version 9 -> 화면은 '변경 있음', revision5 보존
두 탭 저장A/B expected8 -> 조건부 UPDATE 한 요청만 version9
패자 -> CONFLICT + 자기 초안 유지 + 새 대본으로 저장/다시 불러오기
```

저장 응답 순서를 뒤집어도 최신 편집이 저장된 것으로 표시하면 안 된다. 원문 편집과 저장 DB version은 별개 숫자다. 로그아웃은 미저장/미다운로드 경고 후 초안·Blob·query cache를 정리하며 다른 세션으로 재사용하지 않는다.

##### E05/E06. 접근 경계

기존 protectedProcedure 자체에 소유자 정책을 적용해 새 라우터가 기존 패턴만 따라도 보호되게 한다. production은 서버 OWNER_USER_ID 하나, 미설정은 전부 거절한다. 격리 테스트는 서버가 만든 테스트 context에 A/B를 주입하되 HTTP 입력으로 allowlist를 받지 않는다. {A} gate 테스트와 {A,B}에서 각 리소스의 소유자 where 테스트를 분리하고 동일 프로시저/데이터 접근 경로를 사용한다.

X01의 로컬 bootstrap은 원격을 계속 거절한다. 운영 소유자가 없으면 **별도로 승인된 배포 준비 작업**에서 명시한 대상 DB에 공식 Better Auth 계정 생성 경로를 사용하고 결과 user ID를 서버에 설정한다. 공개 가입을 잠시 켜는 복구는 금지한다. 이 작업을 현재 리뷰에서 실행하거나 로컬 계정 데이터를 운영으로 복제하지 않는다.

브라우저가 로그인 쿠키를 악용해 요청을 보내는 것을 막는 origin/CSRF 정책은 RPC·OpenAPI·업로드 모두에 적용한다. 설치된 플러그인을 우선 사용하고 origin 허용을 광범위 wildcard로 늘리지 않는다. 유료 mutation GET, cross-origin simple form, 허용되지 않은 origin/header 조합에서 공급자 호출0을 검증한다. 읽기 실패의 무차별 retry와 원 오류 로그는 안전한 코드·metadata로 대체한다.

##### E07/E08. 관계·입력 경계

개인 연결은 소유자와 대상 ID를 함께 검증하고 가능하면 복합 FK/unique 제약으로 잘못된 소유자 연결을 막는다. 분류 삭제는 연결 해제만 하고 원본 성우·대본은 보존한다. 클론은 deleting 상태를 먼저 기록해 새 연결·새 생성을 막고 기존 dispatch가 끝나거나 확인될 때까지 삭제를 보류한다. 공급자 삭제 성공·로컬 갱신 실패는 tombstone/미확인으로 보존하고 무조건 재삭제하지 않는다.

저장 대본 길이는 초기 제안으로 200,000 Unicode code point/UTF-8 1MiB 중 먼저 닿는 한도, 제목 200자로 제한한다(T5에서 승인할 제품 수치). 생성문 2,000자는 별도이며 공급자 설정·태그를 반영한 최종 입력에 적용한다. 검수 범위는 JavaScript slice와 같은 UTF-16 위치 단위로 기록하고 source revision·해당 부분 문자열·겹침을 검증한다. 표시 글자 수와 위치 단위를 혼동하지 않는다. 부분 재검수는 도입하지 않는다.

#### 2. Code Quality

기존 `utils/orpc.ts`와 `route.ts`의 원 오류 노출은 provider 오류가 추가될 때 비밀을 포함할 수 있는 경계이므로 작은 허용 필드 로거·앱 오류 매핑으로 대체한다. 현재 실제 키 유출이 관측됐다는 뜻은 아니다. 클라이언트 state는 shared provider 하나로 충분하고 provider별 함수·검수 규칙을 거대 클래스나 범용 엔진으로 감싸지 않는다.

C03 복사 버튼은 HTML에 이미 있으므로 새 기능처럼 중복 생성하지 않고 이관 검증으로 처리한다. 분류·프리셋·사용 기록도 동일 voiceRef를 사용한다. 모의 결과는 실제 결과와 타입/표시/기록 namespace를 분리하되 검증·소유권 코드는 같은 것을 실행한다.

설정이 바뀌거나 성우가 삭제된 경우 현재 초안은 복구 가능한 비호환 상태로 남기고 기존 생성 snapshot은 바꾸지 않는다. queryClient 모듈 singleton은 현재 client provider에서 사용하고 있어 요청 간 유출을 입증하지 못했다. 서버 prefetch를 추가할 때 요청별 QueryClient를 사용해야 한다는 조건만 기록하고 현재 취약점이라고 보고하지 않는다.

#### 4. Performance

개인 카탈로그 정보는 로드한 voiceRef 묶음에 대해 한 번에 조회한다. 전체 공급자 목록을 매 요청 모두 가져오거나 즐겨찾기/분류를 성우 행마다 조회하지 않는다. 기록 조회는 `(userId, createdAt, id)` 정렬의 20건 cursor이며 목록 응답에서 대본 전체·바이너리를 제외한다.

카탈로그 query key는 provider·account/public 범위·검색·필터·sort·cursor·세션을 모두 반영한다. 인증/권한/429는 자동 재시도0, 안전한 조회의 일시 네트워크/5xx만 최대1회로 제안한다. 캐시는 계정/세션별이고 로그아웃 때 비우며 비용을 발생시키는 mutation은 재시도0이다. staleTime은 공급자 제약을 확인해 정하고 필터 변화의 정확성을 시간 캐시에 맡기지 않는다.

상한은 선언만으로 충분하지 않다. 최대 텍스트·최대 허용 원본·최대 출력·동시 N을 넣어 서버 RSS/응답 시간·호스트 한도·DB pool을 측정한다. 목소리 수가 10배여도 페이지 크기는 고정하고, 100배 운영은 현재 개인용 계약 밖이라 실제 필요가 생길 때 구조를 재검토한다. 배포 대상 미정 상태에서 임의 p99나 payload 허용치를 보장하지 않는다.
