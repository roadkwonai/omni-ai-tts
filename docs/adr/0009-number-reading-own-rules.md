# 0009. 숫자 읽기 제안은 자체 규칙 엔진이 만들고, Typecast AutoTag는 참고 후보로만 쓴다

- 상태: 결정(2026-11-18, 사용자 결정). 관련: [T11 스펙](../plans/tasks/T11-number-reading.md) 2·4절, [요구사항 5절](../plans/tts-service-requirements.md), 백로그 P0-12.

## 맥락
- 요구사항 5절 5번은 규칙 기반 후보를 기본으로 두고, Typecast AutoTag를 공식 후보로 따로 평가하라고 했다(P0-12).
- AutoTag(`@neosapience/typecast-autotag` 1.14.1, MIT)를 평가했다. 476KB 단일 ESM이고 외부 호출과 런타임 의존이 없다. 다만 상담 전화(ARS)용 읽기를 낸다.
  - `010-1234-5678`은 `공 . 일 . 공 …`(문서 예시는 `공 일 공 다시 …`)로 읽는다.
  - `15,000원`은 `일만오천원`으로 읽는다.
  - 조사 앞에 띄어쓰기를 넣는다.
  - 주소 괄호·이메일 같은 숫자 밖 글도 바꾼다.
  - 애매한 항목(범위·분수·제품명)을 "확인 필요"로 남기는 기능이 없다.
- 우리 수용표(`만 이천오백 원`, `공일공 일이삼사 오육칠팔`)와 맞지 않는다.

## 결정
- 기본 제안은 앱의 순수 함수 엔진(`packages/api/src/number-reading.ts`, T20에서 CLI와 함께 쓰려고 옮김)이 만든다. 수용표 전체를 자동 테스트로 고정하고, 애매한 항목은 확인 필요로 남긴다.
- AutoTag는 숫자 검수 창을 열 때만 동적으로 불러와, 항목 원문의 AutoTag 읽기가 원문과 다를 때 "AutoTag 참고" 후보로 함께 보인다. 사용자가 고르면 직접 입력과 같은 결정이 된다. 불러오기나 호출이 실패하면 후보만 빠진다.

## 버린 안
- AutoTag를 기본 엔진으로 쓰기: 수용표를 ARS식 읽기에 맞춰 고쳐야 하고, 항목별 확인 필요를 만들 수 없다.
- AutoTag를 쓰지 않기: 사용자가 비교 후보로 보기를 원했다(2026-11-18).

## 결과
- 의존성이 하나 늘었다(정확한 버전 고정). 첫 화면 묶음에는 들어가지 않는다.
- 읽기 규칙을 고치면 저장된 결정이 지금 항목과 맞지 않을 수 있다. 결정은 지금 항목과 위치·글이 같을 때만 쓴다(스펙 3절).
