# 0012. 소유자는 세션 + 이메일 한 개로 정하고, owner_id는 외래 키 없는 문자열로 두며, 기존 데이터는 계정을 만들 때 옮긴다

- 상태: 결정(2026-11-18, 사용자 결정 4·5·6·7번). 관련: [T14 스펙](../plans/tasks/T14-owner-login.md) 2·4·6절, [ADR 0004](0004-channel-classification-storage.md)(외래 키를 T14에 정하기로 한 항목을 닫는다), 로드맵 2절(로컬 관리자 모드).

## 맥락
- T1~T13은 로그인 없이 development·test의 루프백 Host 요청에 소유자 `local-admin`을 줬다. production에서는 소유자가 없어 배포할 수 없었다.
- 여러 검사(공급자 voice id 소유권, 성우 캐스팅 '내 계정', 자동 태그 횟수, 프리셋 기본값 교착)가 '소유자는 한 명'을 근거로 미뤄져 있다.
- 데이터 표 8개가 `owner_id text`를 가진다(`provider_list_cache`는 null 가능). drizzle 마이그레이션은 계정·데이터 이전보다 먼저 돈다.

## 결정
- 소유자를 정하는 길은 Better Auth 세션 하나다. 세션 사용자 이메일이 `OWNER_EMAILS`를 정리한 값 **정확히 하나**와 같을 때만 `ownerId = user.id`다. 0개·2개 이상이면 아무도 소유자가 아니다. 로컬 관리자 모드(루프백·NODE_ENV 판정)는 없앤다.
- `owner_id`는 문자열 그대로 두고 `user` 외래 키를 걸지 않는다.
- `local-admin` 행은 로컬 계정 만들기 스크립트가 계정을 만든 실행에서 한 트랜잭션으로 새 계정 id로 옮긴다(목록 캐시 행은 지운다).

## 버린 안
- 개발에서 로컬 관리자 모드 유지: 소유자를 정하는 길이 둘이 되어 검사·테스트가 두 벌이 된다. 배포와 같은 길을 매일 쓰지 않게 된다.
- 여러 소유자 허용: 미룬 다중 소유 보강을 모두 하거나, 알려진 구멍(남의 클론 voice id 사용 등)을 연 채로 두어야 한다.
- 외래 키: 마이그레이션이 이전보다 먼저 돌아 `local-admin` 행 때문에 실패한다. 별도 마이그레이션 순서와 사용자 삭제 동작을 정해야 한다. 소유자 값은 서버가 세션에서만 넣으므로 잘못된 값이 들어갈 길이 없다.
- 이전을 별도 명령으로: 순서를 잊으면 로그인 뒤 데이터가 안 보인다.

## 결과
- production에서도 보호 프로시저가 동작한다(T15 배포의 전제).
- 사용자 행을 지우면 데이터 행은 남고 고아가 된다. 비밀번호를 잊어 계정을 다시 만들 때는 옛 id 행을 새 id로 옮기는 SQL을 함께 실행한다(스펙 9절 절차).
- '단일 소유 예외'는 유효하다. 두 번째 소유자를 받을 때 이 ADR과 로드맵의 다중 소유 보강을 함께 다시 본다. 그때 외래 키(사용자 삭제 시 데이터를 어떻게 할지)도 다시 정한다.
