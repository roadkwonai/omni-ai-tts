# pro-kit 성능 개선 모니터링 기록

pro-kit v0.3.10(템플릿 f406eb60 "화면 라운드 병목 개선과 UI SDK 선택 묶음", 이 저장소 반영 27791e7)의 개선이 실제 라운드에서 효과를 내는지 B 라운드마다 잰다.

이 버전의 개선점은 다섯 가지다.
- 검증 증거 묶음(`dev-cycle packet capture`): 한 번 찍어 봉인하고 리뷰·감사·재확인이 다시 읽는다.
- 함께 시작할 수 있는 행 안내
- 하위 에이전트 감독(`dev-cycle supervise`, 15분 예산)
- 같은 평가자·수행자를 이어 쓰기(SendMessage)
- 구현 전 바닥선(build-floor)

비교 기준은 v0.3.9로 한 MG-09·MG-10 라운드다(같은 알림·모달 영역, 같은 B 대조표).

## 재는 값
- 하위 에이전트마다 걸린 시간(초)과 도구 호출 수. 에이전트 완료 보고의 `duration_ms`·`tool_uses`에서 옮긴다.
- 묶음을 다시 읽은 평가자 수(다시 찍지 않은 횟수)
- 환경 문제로 막힌 시간. pro-kit과 무관해서 따로 적는다.

### 환경 문제(pro-kit과 무관)
- podman 머신과 DB 컨테이너가 꺼져 있었다. 첫 실행 확인이 blocked됐다.
- 로컬 데모 환경 파일에 `DEMO_DB_HOST`가 빠져 있었다(T15b-01 뒤 생긴 변수). varlock이 빌드 때 값을 굳혀 다시 빌드해야 했다. 두 번째 실행 확인도 blocked됐다.
- 두 문제를 합쳐 약 15분을 썼다. 다음 라운드에서는 데모 환경 파일에 `DEMO_DB_HOST`를 넣고 시작한다.

### 중간 판정 (리뷰 단계까지)
- **효과 있음:** 디자인 리뷰(critique A)가 약 5배 빨라졌고 도구 호출이 1/10로 줄었다. 묶음 하나를 세 평가자가 읽었다.
- **효과 없음 또는 이번 표본에서 판단 불가:**
  - 실행 확인은 묶음 capture가 더해져 비슷하다.
  - 구현과 UI 지침 검사는 이번 범위가 더 커서 직접 비교가 어렵다.
- **새로 생긴 이점:** 묶음 측정(가로 넘침·noRing·콘솔)을 audit이 그대로 써서 Main이 다시 재지 않았다.
- **아직 못 잰 것:**
  - 재확인(11행)을 같은 평가자로 이어 쓸 때의 시간
  - 마감 수정을 같은 ui-builder로 이어 쓸 때의 시간
  - `supervise`가 실제로 늦은 에이전트를 잡아낸 사례. 지금까지는 끝난 에이전트를 15분 초과로 잘못 표시한 경우만 있었다.

## MG-11 결론 (v0.3.10 효과)
- **분명한 효과: 검증 증거 묶음 재사용.**
  - 디자인 리뷰(critique A)가 186~216초 / 62~74회에서 40초 / 6회로 줄었다(첫 채점). 재채점은 34초 / 5회다.
  - 묶음 두 개(packet-1·2)를 평가자 넷(critique A, reviewer ui, reviewer code, Main audit)이 다시 찍지 않고 읽었다.
- **효과 있음: 이어 쓰기.**
  - 마감과 재확인에서 수행자·평가자가 스킬을 다시 읽지 않았다.
  - 재확인 실행 확인의 도구 호출이 첫 실행보다 60% 줄었다.
  - 코드 리뷰는 재리뷰 없이 한 번에 끝났다(v0.3.9는 라운드마다 두 번).
- **효과를 보지 못함:**
  - 실행 확인 자체의 시간. 묶음 capture가 더해져 v0.3.9와 비슷하거나 길다.
  - `supervise`가 늦은 에이전트를 실제로 잡아낸 사례가 없었다. 끝난 에이전트를 15분 초과로 표시한 오탐이 1건 있었다.
- **pro-kit 밖의 지연:** 로컬 데모 환경(DB 꺼짐, `DEMO_DB_HOST` 빠짐)으로 약 15분을 썼다. 다음 라운드 전에 데모 환경 파일을 고정해 두면 없앨 수 있다.
- **다음에 이어서 볼 것:**
  - 다음 B 라운드에서 같은 표를 채워 표본을 늘린다.
  - 실행 확인이 묶음 capture와 시나리오를 한 번에 할 때 시간이 줄어드는지 본다.
